# 撤回：通道重启/外部守护式自愈——今后不得再用此手段

> 状态：rejected —— 2026-10-12 用户裁定：「今后都得终止；如果再需要这个手段，一定要用一个更好的手段」

## 决定（否决）

**禁止**以「外部守护进程 + 重启宿主 + 反复注入续跑」作为 run 通道可用性的手段。当晚落地的
`dev/channel-supervisor.mjs` 与 `dev/stream-guard.mjs` 已从仓库删除；run 手册与 dev 工具清单
同步撤行。此路不通的判断依据是当晚一整夜的实测：

- 重启只能换来短暂可用：网络态（VPN/tun）每次切换都会再次弄坏长命进程的 API 链路，于是
  「检测 → 重启 → 续跑」变成循环，用户被卷进一场他无法理解、也无法结束的折腾；
- 重启是**宿主级暴力动作**：它打断所有会话与在飞回合，代价落在无辜的其他 run 上；
- 反复注入「继续」在故障窗口内等于反复烧 token，且用户看到的是"系统一直在自己抽搐"；
- 结论：**让用户感知到"系统在自救"本身就是设计失败**。

## 未来若需要自愈：必须满足的硬要求

1. **用户在环外**：任何恢复动作用户永不需要知道、参与或等待；不需要"切了网络就说一声"这类约定。
2. **请求级处理，不动宿主**：连接/流层面的问题在**请求层**解决（重连、换连接、退避重试、
   按请求新建链路），不得以重启进程、重启通道为手段。
3. **有界且静默**：重试/恢复必须有明确上限与成本上限；超出即如实失败，并把失败说出来
   （产品内的恢复横幅是合格手段——它是**产品内 UX**，不是 shell 级自救）。
4. **不牺牲邻居**：任何恢复动作不得打断无关会话/在飞 run。

满足以上四条的方案才可提交评审；不满足则不做，宁可如实报错。
