# 条目级验收 TDD 化（proposed → implemented 流程纪律）

> 状态：implemented

## 问题

队列条目从 notes/proposed/ 推进到 implemented/ 的过程缺少强制的"先测后做"环节：RFC 验收判据可以是散文，实施可以不预先定义检查方式就动手，收尾可以声称完成而没有判据逐条对账的证据。仓级机械门禁（verify / tests）只覆盖结构与回归面，覆盖不到条目自己的验收——门禁全绿与"条目验收满足"是两个命题。

## 决定

用户定调（2026-10-05）：条目推进遵循 TDD 式手段——先考虑怎么测，实现后看测试满足了吗，反复做对；全程要证据，不随性发挥。落点（判据四型 = 机械门禁 / 契约测试 / 对账命令 / 人工判据）：

- [guides/60 §0](../../docs/guides/60-dev-loop.md) 生命周期增【验收门】判据可检验化：RFC 验收判据逐条绑定检查方式，能机械的先立红（判据在实现前必须能失败）；实施期按红→实现→绿→修→复跑循环；收尾（§4）验收逐条对账，全绿 + 证据在案才算毕业；
- [notes/proposed/README.md](../proposed/README.md) 规则第 6 条同步：验收判据可检验化 + 实施记录载实际红绿证据；
- [00-index](../../docs/00-index.md) 登记 D23（评估先行 D6 的队列条目级投影）。

无法机械化的判据（冷启动走查、语义不重述等判断型）显式标人工判据型并记录走查证据。首个适用条目 = 项目可驾驭性 Phase 1（其 RFC 验收节已按四型绑定检查方式，实施记录按轮载红绿证据）。相邻不取代：[测试策略采纳](2026-10-04-test-strategy-adoption.md) 拥有测试资产与证据形态的分层，本 Note 拥有条目生命周期的验收纪律。

2026-10-05 同日强化（对齐姊妹仓 `ai_dsh_assitant` notes/README §二之三——同日同定调的独立落地，钉版 = [00-index §外部研究材料](../../docs/00-index.md)）：验收门补四条硬边界——①验收写不出可执行检查 = 提案未成熟，回推敲不进实施；②改断言迁就实现不是修法（不许放宽/归一化凑绿，断言只在行为/合同真实变化时同 diff 改）；③未验项不得写 implemented，阻断如实写「阻断 + 原因」；④随性发挥复发 →「implemented 必带真跑命令」升为机械门禁（负例夹具同 diff），无复发不预铺。[notes/README](../README.md) 增「proposed → implemented 的执行纪律」门牌节（指针至 guides/60 §0 与本 Note——一个事实一个家，不复制正文）。

## 输掉的方案

### 只在当前条目执行、不改流程文档

一次性行为不留痕，下个条目回到散文判据；用户要求"内化到流程里"即否决此路。

### 为每类判据新立 verify 门禁

只有跨条目不变的结构性判据是 verify 门禁的形状；条目专属判据（本条的入口矩阵、taxonomy 对账）进 tests/ 契约测试或一次性对账命令即可，升格 verify 会稀释 gate-ledger 信噪比。writing-a-gate 技能的"先想红"纪律仍然适用于真正立门禁的场景。

### 全部强制机械化（消灭人工判据型）

冷启动走查、语义不重述等判据本质是判断；强 mechanize 会产生假牙齿（[floor 门禁教训](../rejected/2026-09-24-floor-gates.md)、[evidence caliber 教训](../rejected/2026-09-24-frontmatter-caliber-gate.md) 同源）。人工判据型要求记录走查证据，不要求伪装成机械断言。
