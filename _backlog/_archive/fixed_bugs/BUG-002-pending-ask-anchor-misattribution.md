# BUG-002：立项后未答的 ask 被锚点折算误标为「交付审阅 ⏳」

> 严重级别：P2（观察面误导——横幅与轨道把"立项三问仍开放"标成"交付审阅等你拍板"，用户会去找不存在的交付审阅卡）｜发现：2026-09-30（0.2.0 适配后 UX 清扫实测）｜状态：已修（2026-09-30 同日）

## 症状

真会话实测（BUG001-验证会话-muo9pqtv，timed ask 超时后 lead 自主立项的场景）：journal 里
唯一的开放 ask 是 **HITL1 三问**（research_type / 深度与篇幅 / 时间口径与语言），但
「研究状态」页签的轨道与横幅显示 **「◆交付审阅（3 问）⏳ / 等你拍板——交付审阅」**——
锚点归属错位：用户会以为交付审阅在等，实际是立项三问仍开放。

## 根因（假设，代码侧已定位）

`hitl-fold.ts` `deriveAnchors` 的锚点归属启发式：`f(交付文件在场) ? passed : q(立项文件在场)
&& tailUnanswered ? anchor-2 pending : upcoming`——**只要 question.md 在场且尾部有未答
ask，一律记到交付审阅名下**，不区分该 ask 的内容属于哪个停靠点。timed 模式放大了暴露面
（v5 谓词让超时 ask 保持"开放"态，窗口从秒级变成持续存在）。设计上"契约外中途确认缀第三
锚"只覆盖**双锚已过**的形态（q ∧ f 都在场），立项后、交付前的中段 ask 落进误标带。

## 复现

1. run 通道开新 lead 会话，发研究请求；
2. HITL1 三问发出后**不回答**，等 600s timed 落定 → lead 按语义继续（立项落盘）→ 回合结束；
3. 打开「研究状态」页签：轨道显示「◆交付审阅（3 问）⏳」+ 横幅"等你拍板——交付审阅"，
   而开放的三问实为立项问题。

## 修复方向（候选）

ask 内容与锚点签名相关：HITL1 三问的 header 集合（研究类型/深度与篇幅/时间口径与语言）
vs HITL2 定稿卡（含"按现稿定稿"选项形态）——`deriveAnchors` 对尾部未答 ask 读其 arguments
的 header 集，匹配哪个锚点就挂哪个；两者都不像 → 缀"契约外确认"第三锚（现有机制扩展到
立项后中段）。纯函数改动 + keyless 矩阵（HITL1 形态 / HITL2 形态 / 无法判型形态）。

## 修复关联

**已修（2026-09-30 同日）**：`hitl-fold.ts` deriveAnchors 归属按 ask 内容判型——HITL1 签名
（首问 header「研究类型」，persona 钦定）→ 立项确认 pending（re-open 诚实态，question.md
在场不掩盖）；HITL2 签名（选项含「按现稿定稿」）→ 交付审阅 pending；无签名 → 契约外
「中途确认」第三锚（原第三锚只盖双锚已过形态，扩到任意窗口）。

**验证**：tests 122/0（+3：BUG-002 主场景 re-ask → 立项确认 re-open / HITL2 签名归属 /
无签名中段 ask → 第三锚；1 条旧断言按修正语义翻新）+ pack 构建 + verify 全绿。**活体分层
如实记档**：目标会话（muo9pqtv）已沉到侧栏折叠区 65+ 深处，cdp-probe/playwright 的列表
展开均无法触达（工具边界，非产品问题）——纠错后的标签在 GUI 里点开该会话即可见，或随
下一场真 run 的立项窗口自然出现。
