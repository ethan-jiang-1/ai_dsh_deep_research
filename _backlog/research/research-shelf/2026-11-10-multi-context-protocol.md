# 多上下文挖掘：一个方向一个上下文

> 性质：研究组织协议。结论直接约束本轮六方向怎么继续，不改 pack 代码。
> 触发：2026-11-10 冷读审计——六个方向里 0 个能只靠目录继续，1 个判 `no`，5 个判 `partial`。

## 0. 结论

**一个方向一个 fresh context，共用一份上下文底座，父会话只做编排/审阅/合并。** 不是一个上下文挖六个，也不是六个互不相干的对话。

## 1. 为什么不在一个上下文里挖完

- **证据基不同**：channel policy 靠 vendor 源码；lens 靠 STORM/persona 研究；quality 靠 self-critique/citation 评测；external 靠产品文档。一个上下文会把它们混成同一种语气。
- **会撞上下文上限**：每个方向要读的源码/论文/模板不同，六个叠在一起会触发压缩，早先的约束（用户原始请求、公司 5 张卡）先被挤掉——这正是冷读审计发现的病。
- **父上下文的价值不是「装下六个」**，是「持有初始意图 + 跨方向约束 + 最终裁决」。它应该 **export** 成共享底座，而不是 hoard。

## 2. 为什么不是六个完全独立的对话

- **共享事实会被重复推导**：角色/通道/lens/证据标准是六方向共用的；没有底座，六份材料会给出六种 `wave` 定义。
- **跨方向冲突没人裁决**：lens 字段、wave 配方、verdict schema 是互相引用的；各自为政会产生不兼容的接口。
- **没有最终综合**：六份材料不等于一个决定；需要一个地方把它们压成 2–3 页决策备忘。

## 3. 三层结构

| 层 | 载体 | 谁维护 | 内容 |
|---|---|---|---|
| 共享底座 | `_backlog/research/README.md` §共享上下文 | 父会话 | 用户约束、仓内必读、机制事实、术语口径、外部证据入口、仓外参照 |
| 方向上下文 | `<dir>/README.md` §本方向上下文 | 方向会话 | 本方向问题/结论、增量必读、外部 URL、已决/未决、完成判据 |
| 会话产出 | `<dir>/2026-..-*.md` v2 | 方向会话 | 论证 + decision table + pilot plan + 「什么会改变结论」 |

## 4. 会话形态：bounded pass vs deep dive

- **bounded pass**（审计、单份 artifact、一次外部检索）：`subagent` / `workflow`，一次性，父级收结果。
- **deep dive**（多轮、要 goal、要反复读改）：**新 conversation** + `create_goal`。
  - 理由：goal 的轮次/续跑属于会话；subagent 是一次性的，goal authority 也受限。
  - 第一消息 = 方向 README + 共享底座 + 一个 objective + 完成判据。
  - objective 写「完成态」，不写待办清单（例：`产出 lens 目录首版 + 题型×lens 矩阵 + 一场 run 的试点计划，证据可核`）。

## 5. 排序：研究自己的 wave

| 波次 | 方向 | 依赖 |
|---|---|---|
| A（并行） | lens-abstraction / orchestration-primitives / quality-loop / external-landscape 第三遍 | 共享底座 |
| B | wave-execution | 需要 A 的 lens 字段与 channel 表 |
| C | research-shelf + 集成 | 父会话 |

理由：wave recipe 的 args 依赖 lens schema 与 channel policy；其余四个可并行。

## 6. 「挖透」的完成判据

每个方向 v2 必须交出五件，缺一不算挖透：

1. **结论**：一句话 + 3–5 条支撑，每条带证据锚点（文件行号或 URL）。
2. **备选与否决**：至少两个被否的方案 + 否决理由（防止只写结论）。
3. **decision table**：选什么 / 为什么 / 代价 / 触发重议的条件。
4. **pilot plan**：在一场真 run 上怎么验，验什么指标，失败算什么。
5. **「什么会改变结论」**：列出会推翻当前结论的外部变化（新 pin、新模型、新证据）。

外加：与相邻方向的交叉链接，且不矛盾；README `> 结论：` 写一句话。

## 7. 父会话的职责

- 维护共享底座（本次已落 `_backlog/research/README.md` §共享上下文）。
- 审每个方向的 v2：事实锚点、是否重复已定事实、是否与别方向冲突。
- 合并成 2–3 页决策备忘给用户拍板；不复制六份材料。
- 不替方向做深挖；不把六份材料塞回一个上下文。

## 8. 反模式

- 一个上下文挖六个 → 模糊、撞限、初始约束丢失。
- 六个对话无共享底座 → 重复推导、术语漂移、接口不兼容。
- 每个方向开 goal 但没人收 → 六个半成品。
- 父会话替子上下文做研究 → 又回到一个上下文。
- 用「材料数 / 字数」当进度。

## 9. 冷读验收

每个方向在开新会话前，先做一次 **dir-only 冷读**：只给目录内文件 + 共享底座，问「能不能继续一层」。判据：

- `yes`：可直接开新会话；
- `partial`：先补**共享底座或本方向上下文**（缺哪补哪）再开；
- `no`：不允许开，先补底座与方向上下文。

**「阻塞项」只算三种**：①方向上下文缺失；②消费者/产出未写；③ claim 无锚点（文件或 URL）。探针未跑、pilot 未做算「待执行」，不算阻塞——不要把「还需要做实验」误判成「上下文不够」。

本轮基线：

- 第一轮（dir-only）：0 yes / 5 partial / 1 no；缺口集中在 source URL、定义、仓内路径、用户约束、完成判据。
- 第二轮（dir + 共享底座）：0 yes / 6 partial，但阻塞项收敛到四类 schema（lens 九字段、evidence 七字段、method-library 四字段、P1–P8）与完成判据冲突——已在共享底座补 §5.1 格式速查、§9 判据优先级、§10 阻塞项定义。
- 目标：下一轮冷读 6/6 无「阻塞项」；仍为 `partial` 只应因为「还要跑探针/pilot」，不应因为「不知道字段/路径/约束」。
- 第三轮（补 §5.2 机制锚点后）：六个方向 **6/6 context-ready**（4 个直接 yes；wave / lens 补锚点后 yes）；剩余全是探针、pilot、真 run 数据，按 §10 不算上下文阻塞。
