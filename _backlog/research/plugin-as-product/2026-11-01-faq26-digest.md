# FAQ 26 结论摘录：产品 profile、目录与数据归属

来源：外部材料 FAQ 26（`_faq_on_digested/26_plugin-as-product/`；问答基线 rc.3，外部材料，非本仓 vendor pin；来源短写 `1f81c047`）。只摘与本产品形态相关的结论；FAQ 原文的 DSH 机制以当前 `vendor/dsh` pin 复核为准（见[机制核验](2026-11-01-dsh-mechanics.md)）。

## 1. 一句话结论

产品型 profile 是 DSH 的启动组合，不是数据隔离边界。每一份事实（插件定义、用户项目、插件状态、产品设置、会话历史、浏览器状态）分别记录 owner、authority、source、mechanism/path、scope/key、readers、writers、可重建性与保留责任；不能给整款产品套一个数据标签。

## 2. 四个空间与归属

FAQ 15 把产品资产分为四类，不是 DSH 的四种存储 API：

| 空间 | 内容 | owner | 本项目的落点 |
|---|---|---|---|
| 发布 bundle | package files、Cordis patch、client bundle、模板/种子 | 包版本 | `packages/deep-research-pack/` 安装副本 |
| 用户项目目录 | 项目文件 | 用户 | 用户启动时指定的工作区 |
| 插件状态 | 索引（可重建）+ 绑定/游标（可能不可重建） | 插件 | 本包不声明 storage domain；运行状态住工作区文件 |
| 产品设置 | profile Config、volatile Settings 或产品文件 | 产品选择作用域 | 启动器设置（上次工作区）住产品 profile 目录，见下 |
| Session 历史 | Session persistence | DSH | `$DSH_HOME/sessions/` |
| 浏览器状态 | browser storage | 浏览器 origin | vendor 键；产品不新增 |

对 Q2（发布包、用户目录、插件状态、设置分别由谁拥有）的答案：发布包只读、用户目录用户所有、插件状态与设置由产品说明生命周期；卸载 bundle 不自动删除任何用户数据。

## 3. Workspace、Session cwd 与权限不是一回事

FAQ 16 区分四个根：

| 名称 | owner | 用途 |
|---|---|---|
| 产品项目根 | 产品 | 产品工具索引或业务数据对应的目录，可不登记为 DSH Workspace |
| DSH Workspace path | Workspace registry | Web 项目导航、Workspace Session 分组 |
| Session `header.cwd` | Session header | 创建时记录的原始工作目录；默认作为 sandbox policy 的 workspace root |
| 有效 working directory | Session working-directory service | 后续相对文件操作与新进程的当前目录；可改变 |

关键结论：

- 只需指定 Session 工作目录时，传绝对 `cwd`；还要加入 DSH Workspace 侧栏分组时，传已有 registration 的 `workspaceId`。两者不能同时传；`workspaceId` 不是 path、权限 token 或产品 project ID。
- `header.cwd` 是不可变的 Session 起点，也是正常 sandbox policy 的默认 workspace root；`working_directory` 可改变后续操作目录，但不改 header 或 sandbox writable roots。
- Workspace registration 不提供文件 API、不赋予模型工具、不拥有目录。删除 Workspace 只删登记，不删目录、文件或 Session history。
- 模型权限来自 preset 可见工具与各 tool provider/policy；Host 插件代码不自动受 Session sandbox 约束，产品工具必须自行校验目标路径与用户授权。
- `workspace-write` 除 Session 根外还允许平台临时目录；读取不受写入 fence 限制。

对本项目：**run bundle 落到用户工作区的前提是 Session 建在该工作区里**（`header.cwd` = 工作区），而不是只把 Workspace 登记进侧栏。登记只服务导航；cwd 才决定 sandbox 根与研究手册注入面。

## 4. DSH Web 首用目录是 DSH 自己的流程

FAQ 16 记录：Web Client 在 Workspace registry 为空且没有任何 live 或 persisted Session 时，才调用 `workspace.initializeDefault()`；Host 在 Documents 下解析 `deepseek-harness/default-workspace` 并登记，随后 Client 创建或复用 blank Session。默认路径属于 Host 账户，不是远端浏览器；失败时 UI 提示用户选择工作区，不会静默切到产品定义的 `<dataRoot>/workspace`。

对本项目：产品不能把"DHS Web 首用目录"当成自己的工作区解析器。产品要么在启动时把工作区注册进 DSH（随后 Web Client 会选中它），要么自建 onboarding；不能依赖 Documents 默认目录，也不能在 Host boot 里等待用户。

## 5. 资产与产物：DSH 没有通用 artifact store

FAQ 14 的结论：

- `present` 只记录文件路径与描述，不复制内容；相对路径按会话 cwd 解析，绝对路径可指向 cwd 之外；文件必须已经在用户可访问的位置。
- `workspace/changes` 是 review 面，摘要只在 Host 内存活到会话销毁，不是持久证据。
- attachments 是给模型读的不可变字节，住 `$DSH_HOME/attachments/v1`，不随项目走。
- spill 是上下文管理产物，默认住 OS 临时目录，不是用户交付目录。
- 会话导出 ZIP 含日志与附件，不含被 `present` 的工作区文件内容。

对本项目：run bundle（`drt_<slug>/`）必须写在用户工作区，交付件用 `present` 声明同一工作区内的文件；不能把 run bundle 写进 `$DSH_HOME` 或附件库。

## 6. 配置层与产品设置

FAQ 17 的 patch 顺序：

```
ordered bundle patches
→ profile cordis.patch.yml
→ $DSH_HOME/cordis.patch.yml
→ 每个 --patch overlay（按命令行顺序）
```

- 覆盖既有 row 的 `config` 是整对象替换，不是深合并；低层 bundle 的非默认字段可能丢失。
- `Config.volatile()` 的 Settings 写回当前 profile patch，不自动跨 profile 共享。
- `dataRoot` 是产品可定义的 Config 字段名，不是 DSH API；产品自建设置需明确 owner、路径、并发、备份、迁移与卸载责任。
- 对同一字段只设一个权威写入入口。

对本项目：启动器的工作区选择不应写进 profile patch（会与用户 patch 和 Settings 竞争）；产品设置用产品自己的文件，运行时路径经环境变量/启动参数传给 Host 插件。

## 7. 安装、升级、卸载

FAQ 18：

- 新 Web profile 从 shipped Web template 初始化，再加入产品 bundle；`dsh plugin` 安装成功只改磁盘上的依赖与 bundle list，不返回 Plugin Manager 的 `ChangeResult.application`；bundle membership 变更后要重启 profile。
- 卸载 bundle 移除依赖与 bundle layer，但不会自动删除产品数据、用户项目文件、Workspace 内容或 Session history；`workspace.delete` 只删 registration。
- 产品负责记录并清理自有状态；不能凭 profile/plugin 名推断用户目录、Session log 或共享 home 数据的所有权。
- profile 不是隔离边界；同一 `$DSH_HOME` 下的 profile 可共享 Session、Workspace registry、凭据与其他 home 数据。

对本项目：产品必须说明哪些数据随工作区保留、哪些随 profile 删除、哪些在 `$DSH_HOME` 且不由产品删除。启动器创建的 profile 与工作区是两种 owner；卸载入口要分别处理。

## 8. 对本项目的直接含义

1. **产品入口**：一个启动器负责装配 profile（不是包内第二 manifest），启动后仍由 `dsh` 承载运行时；不新增第二个应用进程/应用 bin。
2. **工作区解析**：启动时优先 `--workspace` / 环境变量 / 已保存产品设置；否则在启动过程中询问；没有可用路径时 fail-loud，不静默落到 Documents。
3. **Session 绑定**：Host 插件在 boot 时把工作区登记进 `workspaceRegistry`；Web Client 在首屏选中它并创建 blank Lead Session，使 `header.cwd` = 工作区，run bundle 自然落到工作区。
4. **插件内容**：presets、skills、launcher、scaffold/preflight、seed 源、驾驶舱、fetch provider 全部随包；随包文本不得引用仓内 `dev/`、`scripts/`。
5. **数据卡**：pack README 的 10 列数据卡新增启动器设置行；工作区种子、方法库、run bundle、回执、会话/凭据、浏览器状态的 owner 与保留责任逐行写清。
6. **产品设置**：启动器上次工作区用产品 profile 目录下的一个小文件；它不含秘密、可删、不参与 patch 链。
