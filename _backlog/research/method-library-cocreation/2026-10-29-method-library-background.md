# 方法库是什么：给 reviewer 的背景

> 如果只看 UI 会误以为“又一个表单页”。它其实是一个**研究工作台的知识资产**：
> 用户把自己做研究的“打法”写成可复用的四字段条目，研究 Lead 在真正的 run 里按这些条目
> 决定“去哪儿找、怎么核、怎么写、不承诺什么”。

## 1. 一句话与边界

- **方法** = 一套可复用的研究打法（不是一次研究的结论）；
- **方法库** = 本工作区的多套方法（`research-workspace/method-library.md`），工作区共享、不跨工作区（D34）；
- **谁用** = 研究 Lead 在 planning 阶段读取（写进 `question.md` 的方法节），用库条目决定研究怎么做；
- **谁管** = 用户通过「方法库」页（看/存/改/删/设默认）；**方法编辑**（method-editor，D37）是共创者，不是研究者；
- **不做** = 不把库条目回写旧 run；不做排行榜式排名；不替用户拍板；不发明 DSH 没有的机制。

## 2. 数据形状：一条方法长什么样

`method-library.md` 的每条：

```md
## 格局调研（2026-10-12，源自 drt_cn-ai-coding-assistants）

- 找来源: 官方域优先（定价页 / 文档 / 公告 / 更新日志），第三方只当线索与旁证；同一批官方页只钻一遍……
- 怎么核实: 每实体至少一条可核官方源；厂商同域口径不一致并列呈现；关键结论附来源链；口径字段在场……
- 报告怎么写: 先立实体边界，再分节“产品身份 → 计费 → 能力 → 采用 → 趋势”；分档地图 + 竞争轴 + 时效与覆盖边界……
- 不承诺: 不做排行榜式绝对排名；不把未覆盖说成不存在；不做无时间窗的预测。
```

- 文件头写明：**管理动词（看/存/改/删/设默认）只在用户显式要求时执行；库条目只作推荐参考，不回写旧 run**；
- 一个库**至多一条**标〔默认偏好〕；
- 条目可带来源（`源自 drt_…`）与变更记录（append-only 的注释块）。

## 3. 四字段各自的思考（为什么是这四格）

1. **找来源**：研究的第一性问题不是“搜什么”，而是“信谁”。所以第一格钉来源层级（官方/原始 → 第三方线索）、广度与实体边界；
2. **怎么核实**：冲突与数字是研究最容易翻车的地方。第二格钉“两家打架怎么裁、数字怎么回原表复算、口径字段是否在场”；
3. **报告怎么写**：交付物的第一屏给谁看、分几节、什么形态。第三格钉“可读的交付”，而不是“堆证据”；
4. **不承诺**：边界即诚实。第四格钉“这条方法明确不做什么”，防止把没覆盖说成不存在、把判断写成事实。

这四格对应研究方法论的四条线：**来源纪律 / 验证纪律 / 交付纪律 / 边界纪律**（来源 = `research-workspace/method-library.md` 头部注释 + [docs/design/30](../../../docs/design/30-methodology-mapping.md) 的方法论映射）。

## 4. 内置参考（只读）

内置 5 条（`src/lib/config-tables.ts` 的 `BUILTIN_PREFERENCES`，正本 = `research-brief` skill 的方法预设表，三处同钉）：

| 内置 | 一句话 | 用在哪 |
|---|---|---|
| 事实核查 | 核准具体事实/数字/状态的对象、时点与口径 | 单点事实、数字、状态 |
| 领域地图 | 摸清谁在做什么、到哪一步 | 广度铺开、阵营定位 |
| 主张核查 | 查证一个说法是真是假 | 真假判定、反例权重 |
| 方案比较 | 把几个选项放在同一标准下比 | 选型、取舍 |
| 时间线与信号 | 按官方节点排时间线，用预列指标判断走到哪了 | 进展、趋势、信号 |

它们**只读对照**，不能直接套用；用户可“照内置改”成自己的条目。

## 5. 默认偏好

全库至多一条〔默认偏好〕。Lead 在没有更具体的方法时用它；用户可“设默认”。这是“默认打法”与“具体打法”的分层。

## 6. 从 run 沉淀

一次真研究跑完后，用户常想把“这次实际用的打法”存成方法。这是「从这次研究沉淀」的由来：方法编辑读该次 run 的 `question.md` / `final.md`（只读），把实际做法归纳成四字段。**不重跑研究、不改 run。**

## 7. 演进史（为什么现在长这样）

| 时间 | 事件 | 留下的形状 |
|---|---|---|
| 2026-10-12 | 研究偏好模板 + 方法库落地；用户第一条「格局调研」（“把我们这次用的研究做法存成研究偏好”） | `method-library.md` 四字段 + 〔默认偏好〕 + 管理动词纪律 |
| 2026-10-18 | 研究配置面板显式化：看与改为主、四区、就地回执三态 | 面板读 `question.md` 方法节五态如实；判型→打法映射表住 `research-brief` skill |
| 2026-10-21 | 管理块迁入主界面「方法库」tab；右栏只留摘要 | 方法库成为主 tab（Chat/Trajectory 同排） |
| 2026-10-28 | 页内对话共创（D37）：第 5 个 preset method-editor；新建/编辑态三栏；保存走窄工具（D25 修订） | 这就是本 issue 的前身；用户反馈“三栏拥挤/滚动不对”，于是有 2026-10-29 的 A 方案重排 |

相关决定：**D2**（5 个角色，含 Method Editor）、**D18**（研究驾驶舱）、**D25**（研究配置中继面；2026-10-28 修订为方法编辑经 `method_library_upsert` 写库）、**D37**（method-editor 非研究角色）。

## 8. 为什么需要“方法编辑”而不是让用户自己填

- 四字段不好填：用户心里有“打法”，但不会按字段写；直接给空表单，门槛高、易写空话；
- 所以由方法编辑**一次一问**把口语聊成四字段，页面负责“看得见地长出来”；
- 方法编辑不是研究者：不检索、不读 run（从 run 沉淀时只读该 run 的两份文件）、不组队；工具面只有 persona/时钟/skill/ask_user/工作区手册/写库窄工具（D37）。

## 9. Reviewer 的术语表

| 词 | 意思 |
|---|---|
| 方法 / 方法库 | 可复用的研究打法 / 本工作区的多套打法（`method-library.md`） |
| 内置参考 | 5 条只读的官方打法，可照改 |
| 默认偏好 | 全库唯一，Lead 的默认打法 |
| 方法编辑 | 方法库页的共创 agent（method-editor preset，非研究角色） |
| 研究 Lead | 真正的 run 里使用这些方法的 agent |
| run / drt_ | 一次真研究的工作目录 |
| 保存封套 | 页面→方法编辑的保存指令（四字段 + 名称 + 默认） |
| `method-draft` | 方法编辑回给页面的草稿围栏（四字段结构） |
| 来源 / 手改 / 待定 | 每个字段的 provenance，页面上的小标记 |

## 10. 审阅时最该问的三个问题

1. 四字段是否真的覆盖了“研究打法”的关键面？有没有该加的第五格（比如“什么时候换招”）？
2. 内置 5 条与用户自有条目、默认偏好，这个分层是否够用？
3. “方法编辑一次一问”是否真的降低了门槛，而不是把填表变成聊天负担？
