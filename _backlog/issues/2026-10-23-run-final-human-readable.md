# 推敲：run 终稿缺面向人的可读层

> 立卡：2026-10-23 ｜ 状态：推敲中 ｜ 类型：Task ｜ 结论倾向：未定 ｜ 可关闭：否

## 审阅上下文（先看这一节）

- **触发**：用户 2026-10-23 读完 `research-workspace/drt_cn-us-ai-models-hardware/final.md`
  后的原话是“这是一团糟”“我是懂 AI 进来的，都觉得这么多引用、版本、知识地图乱七八糟”；用户
  要的是**人能读懂的终稿**，不是把研究做浅。
- **具体证据（不是“感觉专业”）**：该 `final.md` 427 行；开头 7 个元数据（run / 版本 / 口径 /
  窗口 / 语言 / 类型 / 篇幅 / 立项 / 执行图 / 组队 / 证据链）；§0.1 四条总判断 + 五条可执行含义，
  每句后挂 1–8 个 `[来源:]`；§10.1 是 **30 行判定表**（列：维度 / 状态 / 判据句 / 证据 / 变更）；
  §11 是 **160 张证据卡的来源清单**；全文 76 处行内 `[来源:]`。这些对审计正确，对读者是噪声。
- **期望读者**：懂 AI/业务、但没有读过本 run 的方法论与证据链的人（例如要拿结论做选型/汇报的
  决策者）。不是完全小白；但要求**不先学 AA / ECI / as-of / 等级 / 单源标记**也能读懂。
- **硬约束**：`final.md`/`final/vN` 是 canonical（[D17/D28](../../docs/decisions.md)）；不能为了好读删证据；不能造第二份
  事实；不能加 per-run `AGENTS.md`/静态知识地图（宪章 §7/§11.4）；旧 run 按 epoch 不回溯。
- **不在本卡范围**：改研究结论、重做证据、替代 `final.md`、让所有读者都去读审计面。

**问题与期望结果：** `final.md` 同时承担 Agent/审计面与用户面：来源链、`as-of`、证据等级、
判定表、版本账、内部知识地图、修复记录都在正文。期望交付里有一份**面向人的可读终稿**：
结论先行、理由可懂、影响和不确定性说清；同时保留 canonical 的可追溯性。

**当前情况：** 以上述 `final.md` 为标本；bundle 里没有任何 reader-facing 产物，HITL2 与交付都
只看 `final.md`/`final/vN`。现有 `ResearchFinalTab` 也只承接 `final.md` 路径与 review 静音条；
没有“人读层”的产品面。

**未决问题：** 可读终稿是独立文件，还是 `final/vN` 的第一节？名字是什么（`readable-final.md` /
`final/readable-vN.md` / 其他）？由 lead 写、从 `final.md` 派生，还是 ops/编辑层生成？一份还是
每个版本一份？读者结构是“结论→为什么→对我意味着什么→不确定性→下一步”，还是更短的一页？
哪些内容必须留在正文（反证、未取得、适用范围），哪些可以放到附录/链接？如何保证它不是第二份
事实？

**下一步：** 先按普通读者视角完整读一遍 `final.md`，把“哪几段/哪几类噪声”写成证据；再与流程卡
（[可读终稿流程位](2026-10-23-readable-final-process.md)）一起定合同。不改 `final.md`。

## 已知与未决

- 已知：`final.md` 的引用/等级/版本对 Agent 和审计有用，不能为了“好读”删除。
- 已知：用户要的是“人能读懂”，不是“把报告缩短”；可读层可以比 canonical 短，但不能改变结论。
- 已知：现有 `ResearchFinalTab` 是 `final.md`/`final/vN` 的渲染面，reader 若独立，需要决定它是否
  进页签（见流程卡）。
- 未决：独立产物 vs canonical 的 reader-first 结构；交付/呈现/HITL2 的关系。

## 方案与取舍

- **A. 独立派生文件**（当前推荐方向，未拍板）：`final.md` 保持 canonical；新增 reader-facing
  副本，从 `final.md` 派生，附录链回 canonical。优点是审计面不变；缺点是两份可能漂移，需要
  一致性断言。
- **B. 把 `final/vN` 改成 reader-first**：交付副本先写人话，引用/版本进附录。优点是交付物就是
  人读的；缺点是 `final/vN` 的 canonical 角色被削弱，审计要读附录；会牵动 `ResearchFinalTab`、
  `present`、`node-gate` 门④。
- **C. 只改 `final.md` 的写法**：把正文写浅。缺点：审计信息被压缩，critic/审计无法复核——不做。

## 验收标准

- 一个**没有读过本 run 的领域读者**，只读 reader-facing 终稿，能在 5 分钟内答出：结论是什么 /
  为什么 / 什么会改变结论。
- reader 不新增 `final.md` 没有的事实、数字或来源；关键结论与 canonical 一致；有版本链接与
  “以 canonical 为准”的说明。
- canonical 仍是 `final.md`/`final/vN`；reader 建议 1–3 页，引用/版本/30 行表/160 卡清单压到
  附录或链接。
- HITL2 与交付能同时看到两份，且知道哪份是审计源。

## 需要你拍板

1. 读者是谁：领域决策者（本卡假设）还是完全外行？
2. 形态：A 独立派生 / B `final/vN` 首节 / 其他？
3. 名字与位置：`final/readable-vN.md`、`final/readable.md`、bundle 根，还是页签内？
4. 长度：1–3 页，还是“一页纸”？

- 或经用户拍板并入已有决定（关闭时在状态行记去向）。
