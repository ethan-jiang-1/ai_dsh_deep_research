# 推敲：layering 二代——AST 判法 + import 图守卫 + test 命令钉

> 立卡：2026-10-09 ｜ 状态：推敲中 ｜ 类型：Task ｜ 可关闭：否

**问题与期望结果：** [layering.test.mjs](../../tests/layering.test.mjs)（纯文本 regex ×8）对照 company@59551f2 的四件套有三处真实缺口。出处 = [company 钉版复核 Note](../../notes/implemented/2026-10-09-company-repin-review.md)（候选③）。期望：禁物判法不漏不误、tests 不再能 import 检查驱动（传递引入子进程目前纯靠约定）、test 命令形状被机械钉住。

**当前情况：** 三缺口——
1. **禁物判法窄**：动态 `import('playwright')`（无 `from` 前缀）与密钥间接引用（`const k = '…_API_KEY'`）逃检；同时 `fetch(` 文本正则会误咬夹具字符串（company 已弃用该形态改 AST）。company 现行 = 「任意提及」级 regex（playwright / 密钥名 / credentials.yaml）+ spawn/exec/fetch 族 AST 解析；
2. **import 图守卫缺席且有活暴露面**：`tests/verify-gates.test.mjs` import `scripts/smoke/gates-smoke.mjs`（顶层 import child_process，仅靠 argv 守卫才不在回归层起进程）——company 点名风险形态：「import 进来会把 spawn/fetch 整条带进回归层，文本扫描看不见传递引入」；
3. **package.json `test` 命令无机械钉**：node --test glob 即测试发现配置，被改宽/改坏无人拦。

**未决问题：**
1. **AST 判法在 keyless/stdlib-only 纪律下的实现路径**（本卡核心张力）：company 的解析器在 vitest 生态里，本仓 tests 禁框架禁子进程。候选：vendor 树内是否有纯 JS、零依赖的解析面（先探 `vendor/dsh` 的 test-support/静态分析件）；否则受限括号配对解析（够识别 import/调用形态即止，不求完整 AST）——探明前不定案；
2. **import 图禁令范围**：`scripts/(smoke|probe|run-ops|dist|verify)` 驱动面禁 import，`scripts/lib/` 白名单（本仓 tests 已大量合法消费 lib/，语义同 company tools/lib 例外）；`scripts/run-gates/`、`scripts/run-ops/` 的归属（驱动 or lib 化候选）；
3. **活暴露面的解决方向**：CASES/CONTROLS 搬进 `scripts/lib/`（gates-smoke 瘦成驱动壳）vs 白名单显式豁免——倾向前者（结构解决优于豁免）；
4. 纪律有家句的机器化（company it#4 对 dev-loop §9.1 的存在性断言）——可选项，随主件顺带。

**下一步：** 先探明未决 1 的实现路径（vendor 静态分析面盘点，只读），再定案实施。

## 方案与取舍

- **推荐候选**：探明解析路径后一次窄切片（layering 重写 + CASES 迁 lib/ + test 命令钉 + gates-smoke/verify-gates 连带改）。
- **不采纳**：引入 typescript compiler 进默认回归（违 layering 自身的 keyless 纪律）；照抄 company 的「任意提及」regex 全套（密钥名任意提及会咬 tests/AGENTS 的纪律文本自身——需按本仓文本实测校准误报率）。

## 关闭条件

- 三缺口各自反证实录（动态 import 逃检 → 红；tests import 驱动 → 红；test 命令被改 → 红；各自还原 → 绿）；
