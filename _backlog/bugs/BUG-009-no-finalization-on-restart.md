# BUG-009：挂起回合在通道重启后没有被"终局化"——文档承诺的 turn/end + end-seed 补写不存在，旧 pending 卡残留

> 严重级别：P2（次要——恢复路径能用、旧卡被末位 ask 语义自然取代，无实质危害；但文档描述的机制实测不存在，且双卡局面曾把盘侧谓词钉在假挂起态）｜发现：2026-10-05（系统探针 F：pending 态杀通道重启）｜状态：活跃

## 一句话：这是什么

61 §3/§5 写着：挂起的问询回合在 **web 重启时会被系统"终局化"（补写 `turn/end` + `end-seed`
两个事件）**，之后问询消失、只能靠恢复 prompt 重发。实测：**重启前后日志一个字节都没变**
——终局化根本没发生。这份卡就是把这个"文档说有、盘上没有"的缺口立起来。

## 症状（探针 F 实测，dr_mistral-api-model-list 的会话）

1. lead 抛 HITL1 → **故意不答**，等 600s → timed pending 落盘（75 事件，正常）；
2. pending 态下 `job_kill` 通道（SIGTERM）→ **日志原样 75 事件**——没有 turn/end、没有
   end-seed；
3. 重启通道（漂移绿、web 正常服务）→ **还是 75 事件**——文档承诺的"web 重启时终局化"
   没有发生；
4. 同会话发恢复 prompt → 会话被唤醒（75→90 事件）、lead **原样重发问询**（恢复路径本身
   能用）——但此时会话里出现**两张可答卡**：旧 ask（pending result 在盘）+ 新 ask（重发、
   未答）。
5. 双卡后果实测：新卡被代答落盘后，`hitlPending` 仍为 true——一度怀疑旧卡把谓词钉死；
   复核确认是 v5 折算的**末位 ask 语义**天然取代旧卡（旧卡不参与判定），假阳实为
   **BUG-007 的日志批量落盘**造成的读窗竞态（answer 事件晚于短读窗数秒才可见）。

## 根因（假设）

- **vendor**：宿主重启路径没有做"中断回合对账"（扫描 turnOpen 的会话并补写终局事件）
  ——要么功能缺失，要么从未实现（61 的说法来源待考：可能取自更早 vendor 行为的观察）。
  上游 seam，随 vendor 换 tag 重估。
- **本仓文档**：61 §3/§5 与 `.agents/skills/running-a-research-run` 把"终局化"写成既成
  机制——文档先于事实。

## 复现

```sh
# 1. 起 run → HITL1 抛出后不答 → 等 600s（timed pending 落盘）
# 2. 记下会话日志事件数 N；杀通道（SIGTERM）→ 日志仍 N，无 turn/end
# 3. 重启通道（bash dev/boot-run.sh）→ 日志仍 N（终局化未发生）
# 4. 同会话发 session/prompt 恢复 prompt → 会话唤醒、lead 原样重发问询（恢复可用）
# 5. 会话内两张可答卡并存；代答新卡后 hitlPending 的判定走 v5 末位语义（旧卡无影响）
```

## 修复方向

- **vendor（上游 seam）**：boot 时对 turnOpen 会话做中断对账（补写 turn/end + end-seed）
  ——终局化是恢复语义的天然锚点，值得向 vendor 提；随换 tag 重估。
- **本仓文档（本卡随 diff 已修）**：61 §5 与 running-a-research-run skill 的"终局化"句
  改写为实测行为——挂起回合重启后原样保留；恢复 = 同会话 recovery prompt（可用）；
  旧 pending 卡由末位 ask 语义取代，无需手动清理。
- **代驱工具**：hitl-answer 裁决读窗加有界重试（4 读 × 3s，等谓词不固定睡——BUG-007
  批量落盘下 answer 事件晚于短读窗，同 diff 已落地）。

## 牵出的失败类

**"文档合同 vs 盘侧事实"第三例**（前有 BUG-006 卡的交付门缺口、BUG-007 卡的日志丢尾）：这次是
机制描述本身没有盘面支撑。横切排查方向：61/手册/skill 里所有"系统会自动 X"句式
（终局化、自动续轮、自动归档之类）逐条过一遍盘面验证——写入前先 verify the world。
