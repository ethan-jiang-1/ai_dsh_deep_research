# BUG-033：驾驶舱「业务摘要层」间歇缺"已交付态"三行——同一读取里状态面已 ✅ 而已交付文案缺席

> 状态：排查中 — **间歇**（实测 ~1/5 次红、4 连绿）；无确定性复现；机制假设见下（未钉死）。

## 症状

`client-load-smoke` 的「业务摘要层 = 盘侧 brief-fold 真值（五问逐行对账）」偶发 FAIL，缺的三行**全是
`delivered === true` 分支才产生的文案**（`packages/deep-research-pack/src/lib/brief-fold.ts:164` 起）：
`报告已交付` ｜ `当前版已交付；历史拍板见 question.md §Decisions` ｜
`你现在无需操作；需要继续研究时在会话里提出（补研究/修订表述走交付审阅语义）`。

**关键观察**：同一次读取里，同页的 `交付状态 = 磁盘真值`（由 UI 文本里"✅ 已交付"反推）与
`证据计数 = 磁盘真值`（`face.evidenceCount`）**都 PASS** ⇒ 状态面拿到的 `face.delivered` 为真、
且 face 已加载；**只有摘要层那三行没渲染出来**。

## 证据（2026-10-17）

- 触发场景 = **首个"已交付且已归档"的绑定 run**（会话「跨 harness 约定采纳实况」→
  `drt_harness-conventions-portability`，当日新归档）——即 `delivered=true` 分支此前**从未被这条
  浏览器断言走到过**（在飞 run 上两侧同假，断言恒过）；
- 红：`FAIL 业务摘要层 = 盘侧 brief-fold 真值（五问逐行对账）（缺行：报告已交付 ｜ 当前版已交付；历史拍板见 que ｜ 你现在无需操作；需要继续研究时在）`
  （留档 `runtime/smoke-workspace/cls-brief-intermittent/fail-1.log`）；
- 绿：紧接重跑 **PASS**（同输入、同命令），随后 **10 连 PASS** ⇒ 实测复现率 **1 / 11**（同输入、同命令；
  2026-10-17 两批：1 红 + 4 绿，再 6 连绿）——**低频间歇**，不是确定性缺口；
- 排除项：`delivered` 在客户端只有一个来源（`ResearchStatusTab.tsx:217` 的 `names.has('final.md')` →
  同一 `face.delivered`），摘要 `useMemo` 的依赖数组**含 `face` 与 `steps`**（`:251` 起）⇒ 不是
  "漏依赖"这种静态缺法。

## 机制排查记录（2026-10-17，三条候选逐条排除）

1. **文本形状**（长行被拆成多个 DOM 节点 → `innerText` 插换行）→ **排除**：三条摘要行在 JSX 里都是
   单文本节点（`ResearchStatusTab.tsx:324/325/327` 的 `{brief.stageLine}` 等），`innerText` 不会在节点内插断行。
2. **dev 侧版本变体**（v1/v2+ 文案不同，失败信息把行截断到 16 字故看不出差别）→ **部分排除**：
   `brief-fold.ts:160-183` 的交付分支里，`knownLine` / `actionLine` 是**常量**（与 versions 无关）；
   只有 `stageLine` 随 versions 变体。失败信息同时缺 known/action 两行 ⇒ 只能是**没走进交付分支**。
3. **`uiFace.delivered` 假阳**（宽松匹配 `includes('已交付')` 把非交付态判成已交付，从而不触发重水化循环）→
   **排除**：客户端里唯一渲染"已交付"的位置是 `ResearchStatusTab.tsx:362` 的 `face.delivered && ✅ 已交付`；
   brief-fold 的非交付分支不含该词 ⇒ `includes('已交付')` 是可靠探针。
4. **同引用更新致 memo 不重算** → **排除**：`setFace({...})` 每次新对象（`:204`），memo 依赖数组含 `face`（`:251` 区），
   且 face 内部各值同源同 base（`drt_` → `archive/` → `_abandoned/` 首个非空）。

**收窄后的假设（唯一存活）**：**读点部分水化**——摘要块（`🎯 goal` + 五问）与其上方的芯片
（✅ 已交付 / 证据计数）不在同一帧可用；冒烟在"芯片已到、摘要块未到（或仍是上一 face）"的窗口落读。
支持证据：同一次 `seg` 里芯片类断言全过、摘要类全缺；**排除法后无第二条通路**能产生该组合；
1 红出现在三件冒烟连跑的批次里（负载偏高），此后 27 连绿。

## 机制假设（待钉）

**渲染时序窗口**：状态面与摘要层在同一次渲染里取不同快照——`face` 先落地（状态面 ✅ 已是新值），
而摘要 `useMemo` 那一帧仍持旧值（`delivered=false` 的旧 `face`），到断言读取时刻尚未重算完。
与 BUG-030（回合落定判据）同族：**同一事实的两个派生子各自算、读取侧看不到"哪个才是已落定态"**。

## 修复判据（拟定）

1. **先钉机制**：在读取点同时取"状态面 delivered / 摘要层输入 delivered / 摘要层文本"三值打点，
   复现一次即可判定是"客户端两派生不同步"还是"断言读早了"；
2. 依判定二选一：客户端让摘要层与状态面**同源同快照**（一个事实一个家）；或断言侧**等显式状态**
   （有界轮询到"摘要层与盘侧真值一致"再判，理由 = 浏览器渲染边界，符合 `scripts/AGENTS` 的重试白名单）；
3. 反证：修复后必须能说明"红那一次为什么不会再发生"（例如注入延迟/旧快照复现红 → 修后同注入绿）；
4. 不得用"加重试掩盖竞态"收尾——若判定是客户端竞态，重试不算修法。

## 影响面

驾驶舱**业务摘要层**（用户首屏读的那层）可能在"刚交付"这一刻短暂显示未交付态文案；对已归档 run
的首次绑定会话尤其可见。不影响交付物本身（门禁/审计/报告均在盘上）。
