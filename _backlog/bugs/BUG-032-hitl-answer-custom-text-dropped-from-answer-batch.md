# BUG-032：`hitl-answer --custom` 的文本**未进答复批**——修法指示静默丢失、回合空转

> 状态：**修复落地** — 根因已定案（见 §根因）；判据与顺序修复已落地并 keyless 验证；
> 新判据的**活体验证未跑**（需要一次真实的 `--custom` 作答窗口，如实记）。

## 症状

用 `dev/hitl-answer.mjs --pick 3 --custom "<详细修法>"` 答「修订表述（说明哪段）」这类**选项+自由文本**
的卡时，命令自报成功（盘侧裁决通过、意图对账通过、provenance 写盘），但**lead 收到的答复批里只有选项
label、没有自定义文本** → lead 不知道该改哪段 → 回合结束、什么都不做（操作侧以为已下达修法，实际空转）。

## 证据（2026-10-17 实测，drt_harness-conventions-portability 的 HITL2）

- 命令侧：`第 1 题 ← 3修订表述（说明哪段）`、`盘侧裁决——盘侧复核通过——answer 批 1/1 题实质作答（点击 1 次）`、
  `意图对账通过`、`代理模拟记录已写盘`——**四道自检全绿**；
- lead 侧收到的批（会话日志 `tool/result` 原文，逐字）：
  `{"answers":[{"id":"delivery_review_2","selected":["修订表述（说明哪段）"]}]}`——**无 custom 字段**；
- 后果：操作侧两次下达修法（16 处多文件括号、1 处括号内说明）均未达；lead 两轮 `turn/end` 后静置，
  最终靠 `run-kickoff` **注入**才动（注入通道 = 可靠路径，见下）；
- 对照（同一驱动、不同卡形态）：`drt_cn-moe-2026` 的两问卡上 `--custom` 文本**进过批**
  （该场 question.md 有"答复为自由文本、未选 label"的落账注）——说明**是否进批取决于卡形态**，不是恒丢。

## 根因（已定案）

**UI 契约**：卡片的自定义输入框是**替换选择**语义——同一个问题上「选中某项」与「自定义文本」
**只能留一个**。答复批的两种实测形态即为此：
- 文本进批 = `{"id":"hitl2_final","selected":[],"custom":"<文本>"}`（cn-moe 场，lead 照文本改了）；
- 文本丢失 = `{"id":"delivery_review_2","selected":["修订表述（说明哪段）"]}`（本场）。

**直接肇因 = 操作侧自己的顺序改动**：`db5906b`（2026-10-16）把驱动改成"**先填 custom、后点选项**"
（当时的理由是另一起"空批"事件），于是**点击把刚填的文本清掉** → lead 只看到 label、看不到修法。
旧顺序（先点后填）反而能把文本送达。

## 修复落地（2026-10-17）

1. **顺序按意图定**（`dev/hitl-answer.mjs`）：给了 `--custom` 就让**文本胜出**（点完选项再填，文本进批、
  label 被替换——这正是"答复就是这段话"的语义）；没给就只点选项。注释写清了两种批形态与代价。
2. **进批复核**（判据层 `lib/ask-drive.customLandedInBatch` + 驱动接线）：盘侧裁决与意图对账都只看
   `selected`，所以新增一条——**给了 `--custom` 而批里没有该文本 → 响亮红（exit 1）**，并给出处置
   （长修法改走 `run-kickoff --prompt-file` 注入）。
3. **证据**：keyless 四例先红后绿（形态 `selected:[]+custom` / 只有 label / 空批 / 多题取其一带文本；
   485 → **489**）· `client-hitl-smoke` 回归（未见红，见提交）。

## 验证边界（未跑，如实）

- **新判据的活体验证未跑**：需要一次真实的 `--custom` 作答窗口才能观察"未进批即红"的现场；
  下一次 HITL2 的"修订表述/补研究"档自然覆盖。
- **操作侧口径（已生效）**：**修法走注入（run-kickoff）、签名走卡**——本轮两次修法丢失都是靠注入救回的。

## 影响面

操作侧用 `--custom` 下达修订指示的**全部场景**（HITL2 的"修订表述/补研究"两档都靠自由文本传细节）——
静默丢失会被误当成"用户说了但不细说"，把**操作侧的错**记到用户头上。
