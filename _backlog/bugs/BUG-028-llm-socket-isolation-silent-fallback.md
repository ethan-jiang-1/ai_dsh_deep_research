# BUG-028：隔离守卫自身异常时静默透传原始 fetch——"隔离下"判读可能名不副实

> 状态：排查中（2026-10-15 由 BUG-024 收卡盘点牵出；根因未证）｜发现：2026-10-15（回读 10-13 隔离激活 boot 日志时发现 3 条回退行）｜关联：[BUG-024](BUG-024-direct-path-malformed-storm-recurrence.md)（隔离缓解本体的收卡判据在彼卡；本卡只关"回退失效模式"）

## 症状

`dev/llm-socket-isolation.cjs`（NODE_OPTIONS 预载，LLM 流/web_search 每请求一次性连接）在**自身异常**时走 `catch → 透传原始 fetch` 分支——该请求**未经隔离**（回到全局复用池），而现场只有一行日志：

```
[llm-socket-isolation] 守卫自身异常（透传原始 fetch）: fetch failed
```

10-13 隔离激活那次 boot 的 `runtime/smoke-workspace/web.log` 里有 **3 条**此回退行。危害形态：操作侧以为"隔离在场"（BUG-024 的收卡判据与 triggers 处置序都以此为判读前提），而实际有请求在未隔离路径上跑；若回退是系统性的，整个窗口静默裸奔——正好是风暴会咬人的时段。

## 复现

无法按需复现（隔离件只在 10-13 那次 boot 日志留下 3 次痕迹；此后无通道日志——见 BUG-024 的盘点）。可复核的原始痕迹：`runtime/smoke-workspace/web.log`（该文件被 boot-run 的 tee 覆盖，若已再次启动通道则痕迹消失）与 10-13 的 forensics 目录。

## 根因假设（待证，三条互斥候选）

1. **一次性连接自身失败**（DNS/建连失败）→ 回退。对"本来就会失败"的请求无害，但掩盖失败原因；危害仅限诊断。
2. **守卫初始化/undici 解析在某些进程上异常** → 若走的是这条，则该进程**所有** LLM 流都未隔离（最坏形态）。注意 `undiciOf()` 已有独立的"初始化失败（LLM 请求退回全局池）"文案——本次日志文案不同，故更像 fetch 期而非初始化期，但需证据区分。
3. **上游短抖动下 guard fetch 抛错而 orig fetch 本可成功** → 把可自愈的失败强制变成未隔离请求（放大风险而非降低）。

**判别实验（下一步）**：写一个 keyless 探针，注入系统性故障（如把 undici 解析路径或 dispatcher 构造打坏）与瞬时故障两态，观察回退行计数与请求结果的相关性；再核 10-13 那 3 次回退前后是否有对应的 `turn/end error`（若同行请求最终失败 → 候选 1/3；若无对应失败 → 候选 3 的"本可成功"成立）。同时给回退路径加计数（见修复判据）。

## 牵出的失败类

**缓解措施的失效模式不可见**：对外声明"隔离下"是判据前提，静默回退让声明与事实脱钩；同类 = BUG-025/027 族"检查/守卫自身不可靠"。

## 修复判据

待根因证据确认后写就。方向候选（未选定，按证据取一）：① 回退时 **fail-loud**（计数 + 至少一次"重试仍走隔离"）而不是直接透传；② 回退计数进 boot 日志与观察面，使"本窗口是否发生过未隔离请求"可判；③ 仅当 orig fetch 也失败才回退（先证候选 3 不成立）。判据底线 = 回退路径**可数且不静默**。
