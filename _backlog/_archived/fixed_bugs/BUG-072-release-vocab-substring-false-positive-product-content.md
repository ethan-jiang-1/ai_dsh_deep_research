# BUG-072：release-vocab 的「产品内」子串误伤「产品内容」——合法文案被自家门禁判红

> 严重级别：P2 ｜ 发现：2026-11-12 ｜ 状态：已修 — 取方案 A（收窄门禁词）：`产品内` → `产品内(?!容)`，复合词「产品内容」放行，真正口径「产品内嵌」仍红；门禁头注写明裸子串 + 复合词豁免口径（2026-11-12，去向：none — 门禁修复，审查：agent 自审 + 正则正反例）。

## 症状

新文案指南里一句自然表述被 `release-vocab` 判红：

```
[release-vocab] docs/design/40-research-cockpit.md:300 复活退役词：`props.t`；产品内容（内置打法/领域示范等 canonical 表）**不翻译 canonical 本身**，UI 经显示投影取词，
```

被命中的是 **「产品内容」**——它包含退役词 **「产品内」**（D41 退役词汇之一），但「产品内容」是另一个词
（product content），不是 D41 要退的「产品内…」口径。门禁做的是**子串匹配**，于是合法复合词被判复活。

## 复现

```sh
grep -n "产品内" scripts/verify/gates/b-pack.mjs
# 506: const banned = /…|产品包|产品账本|产品内|P0–P4/
grep -n "产品内容" docs/design/40-research-cockpit.md
# 300:…；产品内容（内置打法/领域示范等 canonical 表）**不翻译 canonical 本身**…
node scripts/verify/verify.mjs --only=release-vocab   # 红
```

## 根因（已证）

`release-vocab` 的 banned 词表对中文做**裸子串**匹配，没有词边界/复合词豁免；`产品内` 作为前缀命中了
`产品内容`。同类风险：`产品面包`、`产品内存` 等含该前缀的词都会被误伤；而 D41 真正要退的是「产品内…」
这一**口径**（如「产品内嵌/产品内的用户」），不是所有以「产品内」开头的词。

## 影响面

- 新文案指南（`changing-ui-copy` 相关条款）需要一个词来表达「产品自带的内容」，现在被迫绕开自然措辞；
- 门禁是**假红**：文档没有复活 D41 词汇，读门禁报告的人会以为文档违规；
- 同类子串词表还有其他潜在误伤（`产品面`/`产品化` 等），但当前实测只有这一处（`docs/terms.md` /
  `evaluation.md` 的枚举行带 `term-policy: allow`，不受影响）。

## 修复判据（二选一，推荐 A）

**A. 收窄门禁词（改 `scripts/verify/gates/b-pack.mjs`）**
1. 把 `产品内` 改为带负向断言的形态（如 `产品内(?!容)`），或从词表移除并靠 `产品化/产品包/产品账本` 覆盖；
2. 先红后绿：注入一行「产品内容」→ 修复前红、修复后绿；注入一行真正的退役口径（如「产品内嵌」）→ 仍红；
3. 在门禁头注写明「裸子串匹配 + 已知复合词豁免」的口径，避免下一位读者以为漏检。

**B. 只改文档措辞**
1. 把 `产品内容` 改为不撞词表的同义表述（如「产品级内容」），不动门禁；
2. 在文档侧注明为何避开该词（否则下一位作者还会写「产品内容」）。

无论哪条：`pnpm test` + `pnpm verify` 绿；`docs/terms.md` 的 D41 词表说明与门禁词表保持一致。

## 修复关联

已落地（2026-11-12，方案 A）：`scripts/verify/gates/b-pack.mjs` 的 `banned` 把 `产品内` 改为 `产品内(?!容)`，并加注释说明裸子串匹配 + 已知复合词豁免。证据 = 正则正反例（`产品内容` → 不命中；`产品内嵌` → 命中）；`docs/design/40-research-cockpit.md` 同一行改回自然措辞「产品文案」（不再被迫绕词）。去向 = none — 门禁修复。
