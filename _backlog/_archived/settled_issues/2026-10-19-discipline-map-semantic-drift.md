## 四项裁决（2026-10-19，逐条带依据）

### 裁决 1：9 行全部「改归类 / 认账改措辞」，**只有一条补门禁**

原卡问「哪几条值得补门禁」。按 `writing-a-gate` §1「能不能由一个固定条件判真假」逐条过：

| 行 | 裁决 | 依据 |
|---|---|---|
| 源 1 #12 | 改措辞 | 判"RFC 是否先于实现"要读时序语义，无法定条件；如实记述观察面走 RFC、persona 侧是事后归纳即可 |
| 源 3 #3 | **补门禁** | 见裁决 2 |
| 源 3 #4 | 改归类 | `count-free` / `doc-now-only` 已是门禁，台账写"未机械化"是事实错误，改准即可；再造 slop 审计 = 把已机械化的换个名字重造 |
| 源 9 #10 | 改归类 | 值域外，改 `不适用` + 引入条件 |
| 源 9 #11 | 改归类 | 同规则不同实现，改 `带证据适配` |
| 源 10 #5 | 改归类 | 静态包裹 ≠ dispose 证据，`照搬` 改 `带证据适配` 并写明盲区（本轮真撞上） |
| 源 10 #8 | 改措辞 | 所称"承重四文件抽检"在 Note 中不存在，删掉这个不实声称 |
| 源 11 #5 | 改归类 + 改指针 | 落点引用错指源 1 不适用行，且载体实际住 `guides/60` |

**不补"禁 commit id 引用"门禁的理由**：按 §1，它**能**由固定条件判真假（正则扫 tracked md 里的
7-40 位十六进制串），但 §2 的代价评估通不过——本仓 `notes/` 里合法出现 commit 哈希的地方是**历史
记述**（"commit 0d9be24 修了 X"），这是 Note 体裁的正常写法，禁掉会误伤整类记忆。上游禁的是把
**指针**写成 commit（"详见 abc1234"），不是禁一切哈希。可判定的窄条件需要判"这句是引用还是记述"，
= 读语境。**结论：不补门禁，改措辞 + 记引入条件**（出现"详见 <hash>"式指针漂移时再补）。

### 裁决 2：真正该补的是「三态值域机检」，不是 commit id

我说的"值得机械化"是**另一件**——本轮核实发现的 6 行值域外。它满足 §1（首词闭集）且 §2 代价小
（一张表、状态列单列判）。**这是本卡唯一新增门禁**，见验收标准 §2。

### 裁决 3：`owns` 截断 → 改存引用锚点，不放宽长度

47/108 条 139-140 字硬截断，完整原文仓内不存在。放宽长度只能保住**今后**，救不回已丢的；而
自由文本无论如何都会漂（上游原文改了，这边不跟）。裁 **改存引用锚点**（源文件 + 节/行），ledger
只记"这条纪律的上游原文在哪"，需要原文时现场读。已丢的 47 条随此不可逆——**如实登记，不假装补回**。

### 裁决 4：语料基线漂移 → 登记待更新 + 可观察重议条件，本轮不重跑

`_digested/` 重跑是独立工作量（需重读 639ed01539 → 687f282e86 之间的 upstream 差异），不属于本卡
"语义修正"的范围。裁 **登记 + 重议条件**（下次换 pin 时必须重跑；或出现"语料结论与本仓现状冲突"
的实例时立即重跑）。**不把"待更新"说成"已对齐"**。
