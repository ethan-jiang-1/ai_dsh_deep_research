# 推敲：门禁自测的 scope——成本在 171 次整树克隆，不在“每案例跑完整 verify”

> 立卡：2026-11-18 ｜ 状态：已结（2026-11-18）｜ 类型：Task（证据基础设施 / 性能）｜ 结论：日常不跑发布档——选择面 `--gate` + fixture 复用（受控 A/B 2.2×）；重档只在发布/nightly ｜ 去向 = [Note](../../../notes/implemented/2026-11-18-gate-self-test-scope.md) ｜ 审查：agent — 受控 A/B + 全量 0 失败 + verify/test 绿 ｜ 可关闭：是（2026-11-18）
>
> **一句话（复核后）**：pre-commit 实测 14s，与自测无关；`gates.e2e` 慢的根因是**每个案例同步
> 整树克隆 + 重建 git 索引**（171 次 × 1797 文件），不是“每个案例跑完整 verify”——fixture 内
> 全量 verify 只要 0.9–1.5s，进程启动地板 20ms。所以“缩 scope”的正确落点是**选择面 + 建仓策略**；
> `--only` 与提高并发实测都无效。

## 0. 复核结论（2026-11-18 本机实测，逐条覆盖卡片原判断）

| 卡片原判断 | 实测 | 后果 |
|---|---|---|
| `--only=<gate>` 把单案例降到 3–4s | `--only` **只过滤输出**，60 道门禁照跑（`context.mjs` 的 `fail()` 过滤 + 入口注释明写“省的是噪声，不是时间”）；实测与全量同价（1.1–1.9s） | **方案 B 作废**：照它改是 0 收益 |
| fixture 内全量 verify 5–7s，启动地板 1.8–2.0s | 全量 0.9–1.5s；`node -e 0` = 19ms，import context = 20ms，import a-docs + 3 个 lib = 23ms | 门禁本体不是成本，B 想省的那部分也不存在 |
| 异步克隆 + `jobs=availableParallelism` → 60–90s | 实测 **293s**，比现状 237s 更慢（10 并发下每案例 13.6s：克隆/add 互相争抢） | **方案 A 作废**：该负载 I/O 受限，并发只加剧争抢 |
| 对照组证明零注入基线全 PASS | 基线实测 8 道红：doc-paths / vendor-pin / vendor-clean / pin-agreement / align-ledger / repo-conventions / staged-change-pairing / hooks-active | 对照组只证“案例自己的门禁 PASS”，不证基线全绿；`expect` 正是为此存在 |
| 59 门禁 / 53 门禁有案例 / “其余 40 门禁” | 60 道门禁；53 道有注入案例；7 道无案例（`NO_CASE_GATES`）；另 13 个正向对照 | 计数以盘上为准，别再按 59/40 规划 |
| pre-commit ~24s | `pnpm verify` + `pnpm test` 实测 **14.0s**（`git diff --check` 毫秒级） | commit 链不慢，不需要动 |

> 绝对值随机器/负载浮动：同一份代码 jobs=4 在本机 237s、在卡片作者机上 333s，约 1.4×。
> **机制判断与机器无关**（`--only` 不减执行、并发不加速、基线非全绿），是代码事实。

## 1. 三个 scope，只有一个该缩

现在混在一起，所以“缩范围”缩错了地方：

| scope | 现状 | 实测成本 | 该不该缩 |
|---|---|---|---|
| **断言面**（一个案例证明什么） | 只断言目标门禁 `FAIL <gate>` | 目标门禁 ~0.05–0.3s；剩 59 道 ~0.9s | 理论该缩，但**价格极低、改造贵**（要动 60 个门禁块或改 `--only` 语义） |
| **建仓面**（每个案例付多少） | 整树克隆 1797 文件 + `git add` 重建索引，全部同步 | **每次 ~0.7s × 171 次 ≈ 120s 串行**，且不随并发下降 | **该缩**——这就是全部痛点 |
| **选择面**（什么时候跑哪些） | 默认全量；`--case` 要手拼 id；文档没说“只跑你改的门禁” | 全量 237s；改一道门禁也只跑全量 | **最该缩**——日常迭代只需要“我改的那道门禁的案例” |

结论：卡片把成本记在“每案例跑完整 verify”上，于是方案 B 去打断言面（收益≈0、改造大），
而真正的两个大头（建仓、选择）没被当成主方案。

## 2. 实测成本结构（本机 10 核空闲，node v22.23.1）

| 配置 | 墙钟 | 与现状比 | 备注 |
|---|---|---|---|
| pre-commit（verify + test） | 14.0s | — | 不在本卡范围，保持 |
| `gates.e2e` 现状（jobs=4） | **237.6s** | 1.0× | user 199s / sys 231s；全程只用到 ~1.8 核 |
| 现状 jobs=10（卡片作者机量级） | 234s | 0.98× | 4→10 并发几乎不涨——已说明不是 CPU 瓶颈 |
| 方案 A：异步 clone + jobs=10 | **293.2s** | **0.81×（更慢）** | 每案例 13.6s；克隆与 git 争抢同一块盘 |
| **fixture 复用 K=4**（本卡推荐） | **102.4s / 107.6s**（两次） | **2.2–2.3×** | 157 案例 + 13 对照全跑，**两次都是 0 失败** |
| fixture 复用 K=10 | 180.1s | 1.3× | K 上去反而变慢：reset 84→176ms，争抢加剧 |
| 现有 `--case` 子集：2 个案例 | 6.9s | — | fixture 构建 2.4s + 对照 1.2s 是固定开销 |
| 现有 `--case` 子集：24 个案例（最大门禁） | 34.9s | — | 克隆串行；复用后估算 ~15s |

单次 fixture 内 verify：0.9–1.5s（0.9s 时部分门禁已红提前返回）。171 = 157 案例 + 13 对照 + 1 基线。

### 复用为什么行、护栏是什么

每案例的 `mutate` 只改 1–2 个文件，`git` 本来就能把它精确还原：

- K 个 worker 各持一份**已 commit 的**基线 fixture（必须 commit：无 commit 时 HEAD 是 unborn，
  `git reset --hard` 会清空索引，接着 `git clean -fdx` 把整棵树抹掉——实测踩过）；
- 每案例前 `git reset --hard` + `git clean -fdx`，再断言 `git status --porcelain` 为空，不空即 fail-loud；
- 每案例后 `git add -A`（stat 缓存已热：整树 13ms，冷态才 174ms）；
- 失败现场照旧保留：失败即把该 fixture 拷到保留目录（只在失败时付一次拷贝）。
- 代价：不再“一案例一份物理副本”，隔离由 git 复位保证；复位失败只会假红（fail-loud），不会假绿。

## 3. 建议的 scope 分级（替代原 A/B/C/D/E 排序）

| 层 | 触发 | 跑什么 | 实测/估算 |
|---|---|---|---|
| **T0 commit** | 每次 commit | hook 现状：`git diff --check` + verify + test | **14s**，不动 |
| **T1 改门禁** | 动了 `checks/verify/gates/**`、`context.mjs`、`gates-cases.mjs` | 只跑**被改门禁**的案例（新增 `--gate=<name[,name]>`；案例表每行已有 `gate`，零新映射） | 1–3 例 ≈ **7s**；最大门禁 24 例 ≈ 35s（复用后 ~15s） |
| **T2 发布/夜间** | 发布候选、nightly | 全量 157 案例 + 13 对照 + 一次基线 | 现状 237s → 复用 **~105s**；若再做真·`--only`（域级跳过）估算 ~60–70s |

T1 是关键：**日常迭代不需要全量**——改了哪道门禁就跑哪道门禁的案例，这是“范围随改动面走”，
不是抽样，也不是静默跳过（末尾自报“仅跑 N 个”，未跑的不计绿）。

改门禁的门禁自测义务因此从“全量 237s”变成“该门禁 7s”，日常提交链保持 14s。

## 4. 实施顺序（取代原 E→A→B）

1. **T1 选择面（先做，收益/风险最好）**：`gates-cli.mjs` 加 `--gate`，驱动壳按 gate 过滤
   `CASES`/`CONTROLS`；`--case` 保留。文档三处同步（guides/60 任务型路由、`checks/AGENTS.md`
   的“改门禁必跑”、`checks/README.md` 的用法行）。新增选项的消费者 = 改门禁的日常环与发布检查单；
   sunset/重估 = 全量降到 20s 以内时（届时选择面失去意义）。
2. **建仓面复用（T2 提速）**：K = 4 个 worker fixture（默认 4，**不要**用 `availableParallelism`）；
   复位 + 断言 + 失败快照按上节护栏。判据 = 同一份 157 案例全量跑两次，红集合与 `--case` 单跑一致。
3. **全量只留发布门**：给一个显式入口（`pnpm gate:release` 之类）+ 文档写清“哪天跑哪条”；
   nightly 已跑全量，不新增常驻负担。
4. **可选、非默认**：真·`--only`（域级跳过未选门禁）把 T2 再压到 ~60–70s。要动 `verify.mjs`
   的 6 个 `runX()` 调用与 `--only` 的既有注释合同；**在 T2 仍嫌慢之前不做**。
5. **不做**：C（按门禁批处理合并 mutation，隔离最贵的地方换几十秒，不划算）；
   F（缓存 PASS，源依赖闭包算漏 = 假绿）；A（异步 + 高并发，实测更慢）。

## 6. 长期架构（修正后仍是两层）

| 层 | 何时 | 跑什么 | 预算 |
|---|---|---|---|
| 日常/commit | 每次 commit | `git diff --check` + verify + test | ≤30s（实测 14s） |
| 日常/改门禁 | 改了门禁或案例表 | `--gate=<被改门禁>` | ≤10s |
| 发布门 | 发布前 / nightly | 全量案例 + 对照 + 基线 | ≤120s（复用后 ~105s） |
| 发布门（严格档） | 发布候选复跑 | 全量 + 关键案例独立复跑 + 证据归档 | 允许更久，不优化掉隔离 |

不再把“把全量压到 40s”当目标：那要靠批处理（C）牺牲隔离，而实测表明复用已经拿到 2.3×，
剩下的差距该由**选择性执行**（T1）而不是**合并执行**（C）来补。
