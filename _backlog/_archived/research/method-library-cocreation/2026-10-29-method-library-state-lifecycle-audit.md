# Method Library Session State and Lifecycle Audit

## Scope and pin

This note audits Session prompt identity, Agent admission and tool execution, Client Session ownership/readiness, crash recovery, and persistence semantics relevant to the embedded Method Editor view. The vendor source inspected is exactly `dsh-v0.2.1-rc.2`, commit `687f282e8625c6b8d11ff58211a90524be2e4317`.

The conclusions below concern that pinned implementation. DSH APIs are not a pack business-operation journal, and provider-specific durability must not be generalized to every `SessionPersistence` implementation.

## Findings

### Prompt admission is not tool execution or result correlation

The prompt endpoint carries a branded `SessionRequestId`; its Host handler copies that value into the user message source as `rpcId`. The command path checks the request identity against both inbox messages and persisted `user/message` history, then returns `{ accepted: true }` once `steer` or `followup` has accepted the message into the Agent inbox. Thus prompt acceptance identifies/deduplicates prompt admission, not model completion or a later business operation result. See `vendor/dsh/packages/api/session-controller/src/types.ts:408-419`, `vendor/dsh/packages/api/session-controller/src/index.ts:455-485`, `vendor/dsh/packages/api/session-controller/src/commands.ts:319-363`, and `vendor/dsh/packages/api/session-controller/src/commands.ts:584-595`.

The persisted `user/message` can also represent synthetic runtime context, not only a direct prompt. On a later Agent step, claimed messages are appended before the model stream is dispatched. These facts do not create a requestId-to-tool-call edge. See `vendor/dsh/packages/core/session/src/types.ts:303-310` and `vendor/dsh/packages/core/agent-loop/src/agent.ts:267-287`, `vendor/dsh/packages/core/agent-loop/src/agent.ts:410-442`.

Tool execution has its own identity. `tool/call.callId` pairs with `tool/result` via the result message source; the result event also cites the originating `tool/call` sequence in `sourceEventSeqs`. This is a call/result relation only. The log-only `request/header` reconstructs the model request header and is not a prompt correlation field. See `vendor/dsh/packages/core/session/src/types.ts:358-403` and `vendor/dsh/packages/core/agent-loop/src/tool-calls.ts:262-290`.

There is a third, separate identifier in the browser Connection transport: Connection mints an `RpcId` for a unary request and checks the response envelope echoes it. It is not the Session `requestId` and does not automatically bind a tool execution to the UI submission. See `vendor/dsh/packages/client/connection/src/rpc.ts:6-16`, `vendor/dsh/packages/client/connection/src/rpc.ts:79-95`, and `vendor/dsh/packages/client/connection/src/client/rpc.ts:34-69`.

### Interrupted tool work has conservative recovery, not exactly-once semantics

Recovery tracks outstanding model tool-call identities. When closing an interrupted log, a started call receives a synthetic `TOOL_OUTCOME_UNKNOWN` error result; an assistant-requested call not yet started receives `TOOL_NOT_STARTED`. A started tool may therefore have performed its side effect before the process failed, even though the log has no actual result. The synthetic result records uncertainty rather than proving execution or non-execution. This is not exactly-once execution and does not supply durable idempotency for a pack operation. See `vendor/dsh/packages/core/session/src/repair.ts:100-198` and the resume description in `vendor/dsh/packages/session/session-persistence/README.md:59-62`.

### Session `append` and persistence `flush` have different guarantees

`Session.append()` commits synchronously to the in-memory log and publishes `session/event` through observer callbacks; the hot path does not wait for I/O, and observer failures do not undo the append. General `SessionPersistence` makes the same distinction at its handle level: a resolved `handle.append()` is accepted and visible on that backend instance, while only a resolved `handle.flush()` promises crash durability. See `vendor/dsh/packages/core/session/src/index.ts:761-827`, `vendor/dsh/packages/core/session/src/index.ts:65-82`, `vendor/dsh/packages/session/session-persistence/src/handle.ts:85-109`, and `vendor/dsh/packages/session/session-persistence/README.md:47-57`.

At the Session layer, `sessions.flush(session)` dispatches the registered `session/flush` durability listeners, awaits their settlement, throws listener failure, and reports whether any listener participated. It is not a method-library file write, a React draft commit, or a general transaction. See `vendor/dsh/packages/core/session/src/index.ts:1306-1336`.

The shipped JSONL provider has a stronger provider-specific physical guarantee: its storage append writes and fsyncs a batch before that storage append resolves; the live router separately observes `session/event` in a bounded buffer and drains it on `session/flush` (and close). A Session append itself still does not wait for that listener or fsync. The base composition mounts this JSONL provider, but the guarantee is not universal to arbitrary providers. See `vendor/dsh/packages/session/session-persistence-jsonl/README.md:75-81`, `vendor/dsh/packages/session/session-persistence-jsonl/src/index.ts:1406-1439`, `vendor/dsh/packages/session/session-persistence-jsonl/src/storage.ts:267-315`, `vendor/dsh/packages/session/session-persistence-jsonl/src/storage.ts:502-569`, and `vendor/dsh/packages/bundle/base/cordis.patch.yml:138-147`.

The standard base also mounts `session-checkpoint-policy`, which awaits `sessions.flush(session)` before a model stream, before top-level tool execution, and before a subsequent step/request boundary; failures stop the downstream model adapter or tool body at those checkpoints. This semantic ordering is composition policy layered over persistence, not an intrinsic guarantee of `Session.append()` or of every deployment. See `vendor/dsh/packages/session/session-checkpoint-policy/src/index.ts:1-18`, `vendor/dsh/packages/session/session-checkpoint-policy/src/index.ts:20-37`, `vendor/dsh/packages/session/session-checkpoint-policy/src/index.ts:52-83`, and `vendor/dsh/packages/bundle/base/cordis.patch.yml:419-422`.

### Client reference ownership, history readiness, and Agent readiness are separate

`retain()` returns an owned `SessionReference` immediately and starts the shared initial `Session.open()` attempt. `reference.ready` is a per-reference, cancellable wait for that attempt to settle; releasing the final reference starts local scope/history teardown. The Client `open()` operation loads Session history, not Host Agent/model/tool readiness. See `vendor/dsh/packages/api/session-controller/src/client/contract/sessions.ts:24-58`, `vendor/dsh/packages/api/session-controller/src/client/sessions/service.ts:285-311`, `vendor/dsh/packages/api/session-controller/src/client/sessions/service.ts:183-230`, and `vendor/dsh/packages/api/session-controller/src/client/sessions/service.ts:586-615`.

Importantly, `ready` settling does not imply the history opened successfully: `doOpen()` catches a `RemoteFailure`, sets `openState: 'error'` and `openError`, then resolves its `open()` promise. Consumers that require usable history must inspect the binding's Session snapshot and require `openState === 'open'`; they must surface or handle the error state. A non-remote exception can reject the open attempt. The snapshot also keeps `promptAttempted` and `awaitingFirstTurn` separate from history opening. See `vendor/dsh/packages/api/session-controller/src/client/sessions/session.ts:393-403`, `vendor/dsh/packages/api/session-controller/src/client/sessions/session.ts:616-643`, and `vendor/dsh/packages/api/session-controller/src/client/contract/snapshot.ts:59-91`.

Host Agent activation is separate again: Session prompt resolution may resume an ordinary Session's Agent, and concurrent resumes are deduplicated. Nothing in the Client reference `ready` promise waits for this Host operation. See `vendor/dsh/packages/api/session-controller/src/agent.ts:195-231` and `vendor/dsh/packages/api/session-controller/src/commands.ts:319-363`.

For the current embedded coach, `ensureCoachSession()` returns `sessions.retain(...)` without awaiting `reference.ready`; `MethodCoachPanel` then publishes the coach id, and `MethodCoachPortal` passes the reference to `SessionProvider`. The DSH scope-area provider resolves a binding and renders it, but does not itself await history readiness. So mounting/publishing this embedded conversation is not proof that history is open or successful. For reliable behavior the view should separately represent acquisition, history loading/open/error, and any send/Agent operation state; releasing the last reference tears down the local Client scope, not necessarily the Host Agent. See `packages/deep-research-pack/src/client/index.ts:193-235`, `packages/deep-research-pack/src/client/method-library/coach.tsx:155-185`, `packages/deep-research-pack/src/client/method-library/coach.tsx:80-98`, `vendor/dsh/packages/client/ui-renderer/src/client/scoped-slots.tsx:504-529`, and `vendor/dsh/packages/api/session-controller/src/client/sessions/service.ts:586-615`.

### Raw follow and Client journal recovery have different cursor contracts

The raw `SessionFollowRequest` has no caller-supplied cursor. Host follow takes its opening cursor from the observed source when each generation opens, publishes that snapshot, then emits later events. The DSH Client `SessionEventStream` wraps raw follow in `RemoteJournalStream`, which privately retains the last-applied cursor but does not send it to Host; a reconnect opens a fresh Host snapshot, verifies its cursor is not behind the last-applied cursor, and replaces the published window. The adapter repairs noncontiguous live events through page reads while an already-open generation is running. It does not promise one-by-one replay of every event across a disconnect. If a pack requires durable-event replay, `session.page` provides a fixed `throughSeq` window and backward `beforeSeq` pagination; the caller must page back from the new opening watermark to its last-processed seq, then merge, order, deduplicate, and apply events. History pages cannot restore process-local assistant frames. The adapter is exported by the Session Controller Client entry point, but using it does not create pack-level operation identity or patch revision. See `vendor/dsh/packages/api/session-controller/src/types.ts:488-509`, `vendor/dsh/packages/api/session-controller/src/history.ts:77-111`, `vendor/dsh/packages/api/session-controller/src/history.ts:120-124`, `vendor/dsh/packages/api/session-controller/src/history.ts:146-175`, `vendor/dsh/packages/api/session-controller/src/history.ts:179-232`, `vendor/dsh/packages/api/session-controller/src/history.ts:392-426`, `vendor/dsh/packages/api/session-controller/src/client/index.ts:13-26`, `vendor/dsh/packages/api/session-controller/src/client/transport.ts:137-203`, `vendor/dsh/packages/api/session-controller/src/client/transport.ts:222-245`, and `vendor/dsh/packages/api/gateway/src/client/journal-stream.ts:83-101`, `vendor/dsh/packages/api/gateway/src/client/journal-stream.ts:115-126`, `vendor/dsh/packages/api/gateway/src/client/journal-stream.ts:261-303`, `vendor/dsh/packages/api/gateway/src/client/journal-stream.ts:305-395`, `vendor/dsh/packages/api/gateway/src/client/journal-stream.ts:533-545`.

The current pack does not use this adapter: its locally defined `follow()` calls `scoped.remote.session.follow()` directly, and `watchCoach()` consumes only live `assistant/message` text. A′ should therefore say to wire the exported Client adapter and handle its failure callbacks, or to implement its own reconciliation around new snapshots; it must not specify a cursor argument to raw follow. Even with the adapter, patch identity, draft revision checks, and business-operation reconciliation remain pack protocols. See `packages/deep-research-pack/src/client/index.ts:60-95`, `packages/deep-research-pack/src/client/MethodLibraryView.tsx:408-488`, and `2026-10-29-method-library-workbench-review.md:298`.

## A′ document assessment

The A′ review's core distinction is sound: prompt `requestId` identifies the UI submission/user message, `callId` identifies the later model tool call/result, and neither is the pack-level `operationId` needed to associate a UI business operation with its tool result. The separate Connection `rpcId` should also stay distinct. The relevant current statements and proposed operation protocol are in `2026-10-29-method-library-workbench-review.md:86-90` and `2026-10-29-method-library-workbench-review.md:236-244`.

The persistence discussion distinguishes the provider-specific JSONL fsync from generic Session persistence, and `sessions.flush(session)` from a business-file/UI-draft commit. Session event observation is asynchronous/buffered, JSONL fsync is provider-specific, and base checkpoint policy adds fail-closed barriers before model/tool work. See `2026-10-29-method-library-workbench-review.md:74-84`, `2026-10-29-method-library-workbench-review.md:94-108`, contrasted with the pinned API/provider citations above.

The main lifecycle correction is more specific than the existing caveat: do not say or imply that awaiting `reference.ready` alone establishes successful readable history. It settles when the initial open attempt settles, including a handled remote failure; the consumer must check `SessionSnapshot.openState/openError`. Also distinguish this history state from Host Agent availability and model/tool readiness. The coach currently does not await `ready` at all, and its `onCoach` callback runs after reference acquisition, not after a verified successful history open. See `2026-10-29-method-library-workbench-review.md:236-242`, `2026-10-29-method-library-workbench-review.md:295`, and the implementation citations above.

The recovery claims are appropriately conservative if phrased as unknown outcome rather than exactly-once or safe-to-retry. A′ acceptance criteria require preserving unknown business outcomes for interrupted tool work: cover both started `TOOL_OUTCOME_UNKNOWN` and not-started `TOOL_NOT_STARTED`, and never report either synthetic recovery result as a confirmed business success or failure or automatically retry it. Recovery evidence: `vendor/dsh/packages/core/session/src/repair.ts:151-198`; current A′ acceptance criteria: `2026-10-29-method-library-workbench-review.md:388-400`.

## Concrete implications for the embedded Method Library

- Treat the Session log as interview/model history, not as the authority for draft field values, manual locks, or a saved/deleted library operation. The pack currently keeps draft state in the view and obtains library content through a read path; neither follows from Session durability. See `packages/deep-research-pack/src/client/MethodLibraryView.tsx:140-183` and `2026-10-29-method-library-workbench-review.md:254-277`.
- Give the embedded view an explicit history-open/error state if it relies on restored messages; do not equate retained reference, mounted provider, Agent running state, or model response with one another. See the readiness citations above and `vendor/dsh/packages/api/session-controller/src/client/contract/snapshot.ts:68-91`.
- Continue correlating prompt echoes by `SessionRequestId`/message `rpcId`; correlate DSH tool events by `ToolCallId` and `sourceEventSeqs`; correlate a method save/delete by a separately validated pack `operationId` and structured result. Do not infer the last relation from prompt text or DSH's tool result link. See `vendor/dsh/packages/api/session-controller/README.md:56`, `vendor/dsh/packages/core/agent-loop/src/tool-calls.ts:262-290`, and `2026-10-29-method-library-workbench-review.md:236-244`.
- On interrupted tool work, keep the business operation in an unknown/unverified state until it reaches an explicitly defined verification criterion. A library read can establish only the target state observed at read time, not which operation produced it. An operation journal establishes that relation only if its commit is transactionally tied to the file mutation. DSH recovery alone does not establish whether an external side effect completed. See `vendor/dsh/packages/core/session/src/repair.ts:157-194` and `2026-10-29-method-library-workbench-review.md:271-279`.
