# 企业高管深度研究搜索 UX

**研究问题：** 在不削弱证据质量和自主研究的前提下，怎样让业务能力强、技术背景差异大的企业高管更容易提出问题、理解研究进展、判断结论可信度并采取行动？

**范围：** 本仓当前的立项、Web 搜索呈现、驾驶舱与交付体验；本仓 pin 的 DSH `dsh-v0.2.0-rc.2` 源码与文档；已有官方深度研究产品资料。本文是设计判断和可测试假设，不是用户研究结果。没有可核对的用户访谈/试用数据，不能断言某种 UI 已提升信任或决策质量。

**日期核对：** 本轮执行 `date '+%Y-%m-%d %H:%M:%S %Z'`，实际输出为 2026-10-11 13:42:29 CST。消费者为本轮用户直派的高管 UX 调研；本文只形成候选建议，不授予实施权限。

## 结论摘要

本仓已具备立项澄清与计划审阅、团队自主运行、证据身份链、对抗审查、交付复审、驾驶舱状态和 HITL 显性化等研究机制；这不代表它们已被表达成高管友好的体验，也没有证据证明它们提升了决策效果。主要待验证的体验问题是如何把这些机制翻译为决策者能消费的信息：**要做什么决定、关键依据是什么、什么仍不确定、哪些变化会改变建议、现在需要用户做什么。**

最值得先试的三项改进：

1. **把立项对齐从“研究类型/深度/口径”补成业务决策简报。** 收集决策对象、待决定事项、决策期限、成功标准/约束；已由用户表达的信息不重复追问。用推荐答案和一句理由减轻技术选择负担。研究类型、篇幅作为系统建议的执行参数，而不是高管必须理解的入口概念。
2. **将等待与进度摘要改写成业务语言。** 保留现有研究轨道作为可选详情；默认首先回答“研究在解决什么、目前已经弄清什么、阻塞/风险是什么、预计下一节点是什么”。运行中不要伪报完成百分比或模型确定性。
3. **让结论可快速核查和行动。** `final.md` 首屏优先给执行摘要、建议/选项、依据、反证与信心边界、决策影响和下一步；关键结论直接链接证据。证据质量不能只靠来源数量或徽章表达。

DSH 当前源码/文档可核验的构件包括：结构化多问/推荐选项、计划审阅、可持续待答问题、搜索的 `queries[]` 并发、来源元数据和截断标记，以及 `present` 交付。DSH 历史会话搜索只在归档实现记录中查到，本轮未核实其当前发布/启用状态，不将其算作现成可用能力。这些构件是否足够支撑高管有效体验仍待验证；候选试验可先复用已核验构件，不先另造提问协议或搜索服务。

## 当前体验盘点

| 环节 | 已有机制与证据 | 对决策者的价值 | 尚未回答的问题 |
|---|---|---|---|
| 立项 | `research-brief` 先查问题模式；一次结构化问研究类型、深度、时间/语言口径；未确认维度标 open；复杂研究呈计划确认卡，快速事实核查豁免 | 推荐项、一次问全、先审计划，可降低反复澄清与明显跑偏 | 三问主要是研究执行参数；未见固定采集业务决策、受众、截止时间、行动标准。现行流程以固定三问为默认基线，命中问题模式的困惑信号时还会叠加对应澄清问；已有 9/29 调研支持澄清按信息充分性触发，须试验评估业务字段是否值得其摩擦 |
| 搜索 | Scout/Analyst 可多路查证；DSH web 支持每次最多配置数量的 `queries[]` 并发搜索、轮询合并去重、返回来源与截断信息；本包工具卡呈现 `web_search` 状态和标题 | 可扩展覆盖面，保留可追溯链接 | 本包搜索卡目前是工具调用摘要，不是高管的“发现摘要”；未直接展示 query 覆盖、来源差异与哪些报告问题已得到回答。底层有多个 query 不等于用户理解其覆盖 |
| 进度/等待 | Cockpit 有人性化活动、轨道、证据计数、交付态；HITL pending 自动显性化并定位到等待节点；队员动作默认折叠 | 用户知道轮到自己时能介入，也可检查研究过程 | 研究阶段术语、计数、队员活动仍偏系统视角；证据文件数不是研究质量。未知是否应把活动流默认收起，需要任务观察，不能仅凭设计偏好裁定 |
| 可信度 | evidence 文件含来源、抓取日期、质量、来源等级、publisher、支持结论等字段；关键结论通常要求两个独立注册域；quick_factual 可单源，但须标为“单源——待破”并在 review 记录风险；critic 查反证与缺口；搜索卡来源可打开并有截断提示 | 研究可审计，不让结论只凭模型口头断言 | 两个来源不必然互相独立或高质量；来源分级不等于证据与结论之间的推理充分；高管需要看到结论会如何影响业务选择，而非仅看到审计字段 |
| 交付/继续 | `final.md` 是当前报告唯一权威副本，由 Lead 用 `present` 显式声明；HITL2 可定稿、补研究、修订表述；rerun 和版本有文件记账 | 研究不是停在聊天答案；可审查并补证 | 尚未证实报告是否适合 3–5 分钟决策阅读、建议如何变成可执行事项、用户能否无需技术协助找到关键依据 |
| DSH 通用能力 | 本仓 pin 的 DSH 结构化问题在断线重连后可恢复；会话内容搜索仅见于归档实现记录，当前发布状态未核实 | 可保留用户可回答的问题；历史会话搜索的价值须待确认当前能力后再评估 | 归档记录不能证明当前可用；即使可用，会话搜索也不是研究结论库/跨项目知识库 |

## DSH 能力映射与社区实践边界

以下机制来源于本仓 vendored DSH `dsh-v0.2.0-rc.2` 的当前源码/文档或 archived Agent Note。它们证明实现形态和权衡，不证明社区普遍采用率，也不等同于经用户研究验证的最佳实践。

| DSH 能力/一手机制 | 本仓映射 | 使用判断 |
|---|---|---|
| `ask_user_question` 一次可提多个带 id、选项和说明的问题；推荐选项置首；默认等待，timed 模式允许独立工作继续且问题可稍后回答 | 现有 HITL1/HITL2 结构化问卡与 pending 显性化 | 保留，语言从研究分类转为业务选择；不要为了“更互动”增加常驻打断。有限等待不等于审批，超时绝不应推断用户同意 |
| DSH `plan-review` 展示计划摘要，给“讨论/批准”动作；通用 question UI 不识别时回退普通选项 | 本仓现有计划确认卡 | 保持计划先审后执行；把摘要写成目标、范围、预期输出和主要未知，不让用户理解 topic 图内部术语 |
| `tool-web` 支持最多配置数量的查询并发，结果按 query 来源标记、交错合并并按 URL 去重；上限和提供方预算明确 | 研究角色可将并行搜索用于多角度查证 | 不要求用户写多个搜索 query。查询策略由系统制定；对用户只呈现它回答了哪些业务问题及来源为何相关。批次失败当前采取全有或全无，若以后变成部分结果，须明确标“覆盖不完整” |
| WebBlock 结构化渲染 answer、完整来源列表、snippet、日期与 truncated；长列表滚动不静默折叠；搜索结果呈现不可信外部内容边界 | 本仓研究搜索活动卡/报告来源链接 | 可借鉴“真实内容可见、截断诚实、可回到来源”；技术原始来源列表放详情层，默认摘要不应变成来源墙 |
| DSH 归档会话搜索实现记录描述即时元数据匹配 + 防抖内容检索、取消旧请求、后端失败保留已有结果并显式提示、结果有界且建议缩窄；当前发布/启用状态未核实 | 高管可能在多个研究会话间找历史决定 | 仅当观察到真实需求时，再确认当前可用性后试验；归档记录不是现成能力证明，也不是研究报告检索 |
| DSH Web 工具呈现结果视图，并对缺失/未知视图回退 generic，卡片保持和模型结果一致并显式暴露恢复路径 | 本仓 ResearchToolCard 简化展示状态和调用标题 | 保留 fail-soft；扩展语义卡需防止卡片让截断/错误/部分结果看起来完整 |

本仓早先的接收路由草稿引用 OpenAI Deep Research、Gemini collaborative planning、Anthropic Research 和 ClariQ 等公开资料，可作为初始先例集。草稿指出不同产品选择澄清、计划确认或直接运行等不同形态，并无一致的“高管专属入口最佳实践”。本轮尝试复核 OpenAI Deep Research、Gemini Deep Research 与 Anthropic Research 一手页面，但三次请求均被网络策略阻断（hostname resolves to a non-public IP），没有取得正文；因此外部产品当前行为仅是旧草稿留存线索，不是本轮已验证事实，也不据此声称高管实效或市场共识。

## 改进候选排序

优先级按用户决策价值、实现摩擦和现有机制重用程度排序；不是未经试用的最终路线图。

| 优先级 | 候选改进 | DSH/本仓复用 | 预期收益 | 代价与风险 |
|---|---|---|---|---|
| P0，可逆试用 | HITL1 加一层“决策简报”：这项研究支持什么决定、谁使用、何时需要、希望采取什么行动；把类型/深度/口径改写为系统建议和影响说明 | 复用现有 ask-user 问卡、推荐项、自由文本、question.md 与计划卡；不加新服务 | 降低用户把模糊业务问题翻译成研究题的负担，提前暴露 deadline/范围错配 | 额外问题会让用户疲劳；采取信息充分性触发，不得把决策字段机械设为每次必答。敏感业务约束可能不适合默认写入更广范围工作区 |
| P0，可逆试用 | 试验活动摘要是否按“目标/已经知道/仍未解决/重要风险/下一步”组织，并将人员与工具细流作为可选详情；这是信息架构和内容呈现候选 | 复用 follow/journal、activity-fold、bundle 状态、右栏和现有等待横幅 | 降低技术噪声，等候时说明为什么要等 | 从日志自动压缩可能误报发现；所有总结必须链接到可验证文件，数据不在场要显示未知，不得生成虚假百分比或 ETA。不是品牌皮肤或高管专属产品化授权 |
| P0，可逆试用 | 报告第一页改成决策摘要：推荐动作（或不应下结论）、备选、影响、关键依据、反证/未知、有效时间与下一步；随后是结论详述和来源 | 复用 `final.md`、evidence 直接引用、critic review、`present` 和已有版本制度 | 让用户先作决定，再按需审计，而不是先读方法细节 | 不应强迫报告给唯一推荐；预测、财务或法律影响必须标注口径和假设；语言润色不能掩盖证据缺口 |
| P1，基于使用证据 | 若试用证实有需要，再给状态和报告设定简洁/详情两层：简洁为业务状态，展开才显示 phase、topic、队员动作、来源材料；仅限信息架构与内容呈现 | cockpit 现有折叠区、tab 与结构化报告 | 同时照顾想快速判断与想深查的用户 | 增加 UI 分支和信息一致性维护；每个字段要有单一事实源。驾驶舱例外仍限研究观察/调试，不包含品牌/皮肤；品牌需求须按 UI skin 否决记录的条件由用户明确重启 |
| P1，验证后 | 搜索结果摘要按业务问题聚合：支持/反驳/背景，显示来源发布日期、独立来源覆盖与缺口，点开回 DSH 来源详情 | `queries[]` 标签、WebBlock 来源、evidence frontmatter、topics 的 must_answer | 把搜索活动转成决策证据，而非工具记录 | 来源主题归类和支持/反驳判断本身会出错；多来源不能自动代表真相；必须做文件证据对账和人工反例评测 |
| P2，触发后 | 跨 run 历史研究检索/决策索引 | 可探查 DSH `session.search`，或用现有档案定位做试点 | 降低重复研究，帮助发现过去假设与决定 | session.search 不等于 bundle/final 的语义索引；新建知识库会带来权限、时效、冲突与维护负担。未见足够重复查找问题前不建 |
| 暂不建议 | 将用户常驻带入 team 任务板、提供实时 token/工具/队员监控、暴露可编辑搜索 query 工作流、另建控制台或多套状态系统 | DSH 有 teams、tools、journal，但已有主通道与 cockpit | 对技术管理员可能有用 | 与高管日常任务价值弱相关；扩大认知负担，并重复现有事实源或引出维护/安全面 |

## 可直接试写的业务卡与交付样例

以“明年是否进入东南亚市场”为例，第一段以现有固定三问为默认基线，若命中模式库困惑信号则照现行规则叠加澄清问；推荐内容改成业务语言：①“建议比较进入、试点、暂缓三种选择，而非只收集市场资料”；②“建议先给一页决策摘要，附详证；全面调研会增加等待与取证量”；③“建议以最近完整年度与可获得的最新监管资料为口径，中文交付”。不能给无法测量的固定完成时间。用户已经说明的受众、地区、预算、期限直接进入计划摘要；缺项先标“尚未确认”，仅在会改变研究范围时追问。本建议不等于将默认三问机械升级成固定四问或重开 HITL1；现行模式命中澄清规则仍适用，永久调整需另按交互合同处理。

计划卡展示：“决定：是否试点；比较：进入/小规模试点/暂缓；必须回答：需求、准入、渠道和盈亏约束；暂不覆盖：逐企业销售线索；交付：一页摘要＋来源；尚缺：预算上限”。仍使用现有按计划开跑/修订/放弃动作。高管看到的是选择的影响，内部的 topic、编制、查询词留给团队执行。

报告首屏建议采用六个短段：建议与适用条件、三个选项的收益/成本、最关键的三条依据、最强反证、目前不能判断的事项、下一步负责人/期限（未获用户指定时标待定）。例如“只有满足渠道试点预算上限和准入条件时建议试点；利润预测缺可靠成本数据，目前不能支持全面进入”。每条关键依据保留证据链接；附件再给原文与口径。此为格式样例，不是东南亚市场的事实结论。

进度摘要必须区分“已拿到来源”与“已形成结论”。可写“已取得准入政策资料；市场规模的两种统计口径尚不一致，正在核对”，前提是 findings/evidence 真有这些事实。只有工具事件时写“正在核对市场规模来源，尚未形成判断”；不要从搜索 query 或文件数推断已经弄清市场。

本轮 notes 检索命中并阅读了 [HITL 反馈协议否决记录](../../../../notes/rejected/2026-10-06-hitl-feedback-protocol.md)：DSH 选项本身已经承载接受/修订语义，当前没有机器判读自由文本反馈的需求，因此不建议另加 `[ACCEPTED]` 等协议。还阅读了 [UI skin 否决记录](../../../../notes/rejected/2026-09-24-ui-skin.md)：研究驾驶舱与品牌皮肤目的不同；皮肤需求仅在用户点名 demo/品牌需求时重启。本文驾驶舱建议仅指信息架构/内容表达试验，不包含品牌化或高管专属皮肤，也不构成其授权。检索还命中计划确认闸门、驾驶舱流程与真人验收记录；未展开的历史条目不充当本轮已验证证据。

## 试用与验收

先拿 5–8 个代表性业务问题做低成本对照试用：分别覆盖快速事实、市场/竞争格局、断言核验、趋势/预测类问题；至少包含不熟悉 DSH 的业务读者。样本数用于发现明显摩擦，不足以证明统计显著的效果。让用户以自己的工作语言输入，不先教其研究分类。

建议每场记录任务时长、用户主动改写次数、HITL1 修改计划次数、是否能在 30 秒内复述要做的决定与最大未知、能否在 2 分钟内找到支撑建议的来源、是否误认未完成/部分结果为完整、HITL2 选择以及后续补研究原因。记录实际行为与原话，不以“觉得不错”替代。

进入实现前可采用这些初始验收判据（阈值属于试点假设，应先测基线）：

- 用户看完立项卡后能用一句话准确复述研究支持的业务决定；若不能，系统先给一版简报并只追问会改变计划的缺项。
- 用户不需要知道 `quick_factual` 等 token，也能理解系统建议的研究投入及其成本/时效取舍。
- 未打开技术详情时，用户能说出已确认事实、最大未决和下一次需要其动作的时机；不能以 evidence 数量冒充进展质量。
- 任取一条关键结论，用户能从报告跳到真实来源和对应摘录，并看出它支持、反驳还是不能回答该结论。
- 失败、超时、截断、单源、争议、过时口径均显性表示；内容不足就表达“目前不能判断”，而非用流畅文字填空。
- 对照原有 UI，新增提问/信息负担没有抵消理解收益；若活动详情或覆盖分析很少被看，默认层应相应变轻。

具体试点分两步，先只改问卡文案和报告试写，不改运行拓扑：第一步用 6 份已脱敏任务与配套报告做探索性对照；将每项任务分别制成原版/新版摘要，读者按随机且平衡的顺序阅读，同一任务两版之间安排间隔并记录顺序，以便任务内比较、降低记忆影响。盲法仅针对版本假设，不称为严格双盲；整理者知道版本，读者不告知哪版是候选。第二步让 3–5 名不熟悉 DSH 的业务决策者各完成至少两种不同类型任务；不要求小样本覆盖全部题型，以逐人记录卡住点、误解、改写和来源查找为目的。观察者不代答问卡。成本包括整理样本、两版试写、访谈与记录；驾驶舱开发在前两步之后再决定。

这些数值仅作探索试点的观察目标，不是统计结论或上线门槛：记录每位参与者能否在 30 秒内复述决定与最大未知、能否在 2 分钟内找到依据及原始链接、立项耗时相对其任务基线的变化。可把 80% 理解/查找率与立项中位耗时增加不超过 20% 作为下一轮讨论的假设目标，并同时列出原始人数、任务数与失败案例，不推广到总体。任何把搜索摘要、截断结果或单源结论误认成已核实的情况都作为严重问题复盘和暂停扩大的信号，而非用极小样本计算稳定通过率。若理解提升但立项负担明显增加，先缩短默认文案；若核查失败，优先修报告证据导航；只在进度理解持续失败时试验驾驶舱业务摘要。

日志/观察需遵守 run 的数据权限与敏感信息约束；用于试点的题目和报告按企业材料处理，不将真实机密内容送入外部评测服务。

## 实施建议

不要先改 DSH 核心、引入新包或改变团队调度。先用现有问卡和报告模板完成一轮可逆试写，再由高管型读者走真实入口。只有反复观察到“找不到目标结论、来源或前次决定”后，才讨论驾驶舱的信息架构/内容呈现或历史检索能力。驾驶舱例外仍仅限研究观察/调试；品牌/皮肤面不因本研究纳入。若用户明确提出 demo/品牌需求，应依 UI skin 否决记录的重启条件另行处理。若后续改动永久改变用户交互/报告合同，按该变更性质更新相应 owner 文档，并用真实组合及面向用户的试验验证。
