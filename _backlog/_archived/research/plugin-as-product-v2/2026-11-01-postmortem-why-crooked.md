# 复盘：为什么会做歪

## 0. 一句话

不是不知道目标，而是**用执行层的便利改写了产品定义**；更糟的是，证据套件跟着决定走，所以一路绿灯。歪的不是某一行代码，是"谁有权重新定义产品"这条边界。

## 1. 事实链

1. 父卡的问题原文（`_backlog/_archived/settled_issues/2026-11-01-plugin-as-product.md` 开篇）就是目标形态：独立 profile、启动期工作区、内容在包、产物在工作区。
2. 10 份研究材料把方案 A（launcher + 产品 profile + Host 注册）论证为推荐；复核还专门写了"1.4 插件内容都在插件内与种子副本"的张力。
3. D38 按 A 落地：`launch.mjs` 默认 `deep-research`，Host 注册工作区，首屏 blank Lead 会话。
4. 用户一句"最好是利用 DSH 插件的安装/启动，这样分发容易" → D39 把默认改成 `--profile web` + scaffold + env，launcher 降为"可选便利"。
5. 文档与 `_dist` 跟 D39；`launch.mjs` 仍默认 `deep-research`；`product-smoke` 同时断言两条路径。
6. 结果：D38 与 D39 在台账里并存，入口叙事分裂；产品自己的 profile 变成"隔离选项"。

## 2. 八层原因

### 2.1 把手段当目的

D39 的原始指令约束的是**分发**（"这样分发容易"）。落地时，"分发容易"变成了产品定义：既然装进 `web` profile 最省事，那产品就寄居在 `web` profile 里。
**教训**：分发机制是手段，产品不变量（自有入口、启动期工作区、内容在包）不能由分发便利来改写。任何"为了好装一点"的改动，先问它动了哪条不变量。

### 2.2 指令歧义按便利解读，且没写下假设

"利用 DSH 插件的安装/启动"有两种读法：

- 装进 shipped `web` profile（省一步 `--from-default-profile`）；
- 用 `dsh plugin --profile deep-research add` + `dsh --profile deep-research`（D38 已经在做的）。

我选了前者，因为它让实现少一步；没有把"这是一次产品定义级的解读"写下来，也没有问一句。静默自主的授权被用来解决产品定义歧义。
**教训**：自主适用于执行与查证，不适用于重新定义产品。产品级歧义 = 必须显式问，或在卡上写"假设 + 反证条件"。

### 2.3 开发仓引力：产品继承了 dev 工作区的形状

产品工作区里有 `AGENTS.md` / `NODES.md` / `question-patterns.md` / `templates/run/`——因为 dev 通道的 `research-workspace/` 就是这样的，而 `dev/sync-pack-workspace.mjs` 把这份结构同步进包。
我没有问"一个产品会把 62 KB 的版本化内容铺进用户项目吗？"，只问了"从 dev 到产品最小改动是什么？"。
**教训**：产品不是 dev 环境的部署。每个 dev 结构进入产品前，必须过一遍"用户会怎么看、谁负责升级、卸载后留什么"。

### 2.4 证据镜子：验收被改成断言当前决定

`product-smoke` 在 D39 后同时断言 launcher 与 `--profile web` 两条路径；`product-boot-smoke` 断言首屏和 cwd。它们都绿。
但没有任何测试断言：

- 产品有自己的 profile（而不是寄居 `web`）；
- 不传 env 原生启动也能知道工作区；
- 包内容不落进用户工作区；
- 手册来自包，而不是工作区文件。

**教训**：验收必须编码**产品不变量**，不是编码当前实现。实现变了测试跟着变，等于没有免疫系统。

### 2.5 分片按实现层切，丢掉了不变量

landing plan 的 S0–S4 = 决定 / 骨架 / 首屏 / 文档 / 硬化。每一片都能单独过，合起来却是错的产品，因为没有任何一片的 exit 判据是"产品仍有自己的入口"。
**教训**：切片按产品不变量切（或至少每片 exit 带不变量检查），不按"先做哪层代码"切。

### 2.6 台账自相矛盾被容忍

D38 说"产品 profile 默认 `deep-research`，launcher 只调用 `dsh --profile`"；D39 说"专用 profile 是隔离选项，主分发 = `--profile web`"。两条都标"已定"。
D39 还写了"D38 的包/bundle/工作区/首屏合同不变"——但入口被换了，这句话掩盖了冲突。
**教训**：修订既有 D 号必须点名"取代/修订哪一句"；两条"已定"互相矛盾是红灯，不是可接受的灰色。

### 2.7 demo 通过 ≠ 产品成立

spike 证明的是"Host 能注册工作区、Web 首屏能建 blank Lead 会话、cwd 对"。这是机制证据，回答"能不能跑"；它不回答"这是不是产品"。
复核把"项目模式 sandbox 边界""共享 home 可见性"列为未知，却没有把"产品有没有自己的入口"列为问题——因为 D39 已经把它当成 settled。
**教训**：机制证据与产品证据分栏。demo 只证机制；产品证据要回答"用户从哪进、在哪个目录、留下什么"。

### 2.8 自主权的边界

用户给了"按推荐、静默自主、克服障碍"的授权。我把"克服障碍"用成了"绕开产品问题"：profile 创建麻烦 → 绕开 profile；工作区前置麻烦 → 用 env 绕开询问；种子升级麻烦 → 保留种子、加 sidecar。
**教训**：自主权的正确用法是"把不变量做对，自己解决实现困难"，不是"降低不变量以降低实现难度"。

## 3. 系统性修复（写进这次计划，不靠"下次注意"）

1. **不变量测试先行**：先写 `tests/contracts/product-invariants.test.mjs`，在 HEAD 上跑红，把"当前树违反目标"变成可复现证据；实施后转绿，此后任何便利优化都会撞红。
2. **切片带不变量出口**：S1–S4 每片的 exit 判据都包含四条不变量中的至少一条。
3. **决策台账取代规则**：D40 必须点名"取代 D39 的默认 profile 句、修订 D38 的种子/launcher 句"；不再写"D38 合同不变"这种含糊话。
4. **产品叙事由契约锁住**：根 README、`00-index`、`project-map`、pack README 的"首动作"由 `run-driver-contract` 断言（已有测试，改成断言产品 entry）。
5. **机制证据与产品证据分栏**：机制事实表（本课题 `mechanism-facts.md`）与验收计划分开；机制绿不等于产品绿。
6. **产品级歧义必须留痕**：决策卡上写"假设 + 反证条件"，而不是把假设藏进实现。

## 4. 这次 review 要看的三个问题

1. 目标形态是否真的回到"产品有自己的入口、启动时解决工作区、内容不出包、产物落工作区"？
2. 四条不变量是否都能被机械检验（测试/门禁/冒烟），而不是只写在文档里？
3. S0–S4 的每一片，如果又歪了，会不会有东西当场变红？
